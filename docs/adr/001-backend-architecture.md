## 1. สภาพจริงที่ตรวจแล้ว (Context)

ตัวเลขทุกตัวในส่วนนี้ผมเปิดไฟล์ตรวจเองวันที่ 23 ต.ค. 2026 ไม่ได้อ้างจากสรุปของใคร ทุกข้ออ้างอิงไฟล์และบรรทัดให้ตรวจซ้ำได้

| สิ่งที่ตรวจ | ผลที่พบ | หลักฐาน |
|---|---|---|
| build step | ไม่มี `package.json` ทั้งรีโป ไม่มี build ไม่มี backend | `git ls-files` 240 ไฟล์ ไม่มี `package.json` |
| ไฟล์วิดีโอ | แท็ก `<video` ทั้งรีโป = **0** | `grep -r "<video" . --exclude-dir=.git \| wc -l` → `0` |
| แหล่งข้อมูล | อยู่ใน global `window.LAKORN` ไฟล์เดียว 2 บรรทัด 36,008 ไบต์ | `assets/data.js` |
| ปริมาณ | 12 เรื่อง · 418 ตอน (`eps` รวม = 418 เท่ากับจำนวนสมาชิก `episodes[]` รวม พอดี) | คำนวณจาก `assets/data.js` |
| คุณภาพชื่อตอน | 418 ตอน มีชื่อไม่ซ้ำกันแค่ **32 ชื่อ** → ซ้ำเฉลี่ย 13 ครั้งต่อชื่อ | คำนวณจาก `assets/data.js` |
| ฟิลด์ที่มีจริง | `slug` `title` `genres` `eps` `status` `c1` `c2` `cast` `hook` `episodes` — **เท่านี้** | union ของคีย์ทั้ง 12 เรื่องใน `assets/data.js` |
| ฟิลด์ที่ยังไม่มี | `synopsis` `tropes` `releaseDay` `cover` `views` = มี 0 จาก 12 เรื่อง — **แถวนี้ล้าสมัยแล้วตั้งแต่ commit `77bc352` ดู §12.4** | union เดียวกัน |
| HTML ว่างตอนส่ง | `watch/*.html` **12/12 ไฟล์** มี `<h1 id="epTitle"></h1>` ว่าง JS เติมตอน runtime | `watch/ceo-cold.html:36` · เติมที่ `assets/app.js:111` |
| structured data | JSON-LD ทั้งรีโป = **0 ไฟล์** | `grep -rl 'application/ld+json' --include=*.html .` → ว่าง |
| โดเมน | ไม่มี `CNAME` ในรีโป | `git ls-files` |
| ม็อกอัพที่อนุมัติ | `design/v2/` มี generator จริง `build.mjs` + `lib.mjs` + `pages-*.mjs` — **Visual เป็นเจ้าของ ห้ามแก้** | `design/v2/` |

### 1.1 สามเรื่องที่ผมเจอเพิ่ม และมันเปลี่ยนรูปของงาน

**(ก) ธงล็อกตอนมีความหมายกลับด้านจากที่อ่านเผิน ๆ และของจริงล็อกไว้ 298 ตอน**

`episodes` เก็บเป็น tuple 3 ช่อง `[ชื่อ, "m:ss", ธง]` ทั้ง 418 ตอน ธงช่องที่สามไม่ใช่ "ล็อก" แต่คือ "ดูได้" — ค่า `false` คือตัวที่ถูกล็อก ดูที่ `assets/app.js:118` ใส่คลาส `lock` เมื่อ `x[2]` เป็นเท็จ และ `assets/app.js:123` เด้ง toast `'ตอนนี้สำหรับสมาชิก'` เมื่อ `!s.episodes[ep-1][2]`

นับจริง: `true` (ดูได้) = **120 ตอน** · `false` (ล็อก) = **298 ตอน** จาก 418

แปลว่าวันนี้เว็บยังล็อก 298 จาก 418 ตอน ขัดมติ "ดูฟรีทุกตอน" อยู่ในโค้ดที่ยังรันได้ ใครจะทำ migration ต้องรู้ว่าทิศของธงคือทิศนี้ ไม่ใช่ทิศตรงข้าม เพราะถ้าอ่านกลับด้านจะเผลอล็อก 120 ตอนและปล่อย 298 ตอน

**(ข) เรื่องย่อซ้ำประโยคโปรย — พบตำแหน่งที่ทำให้มันซ้ำแล้ว**

ในม็อกอัพที่อนุมัติ หน้ารายละเอียดเรื่องพิมพ์ `s.hook` สองครั้งติดกัน: `design/v2/pages-discovery.mjs:535` พิมพ์เป็นบรรทัดนำ แล้ว `design/v2/pages-discovery.mjs:537` พิมพ์ซ้ำอีกครั้งเป็นต้นประโยคของย่อหน้าเรื่องย่อ ไม่ใช่ความพลาดของ Visual — `assets/data.js` ไม่มีฟิลด์เรื่องย่อให้ใช้ จึงต้องหยิบ `hook` มาใช้สองหน้าที่ นี่คือเหตุผลที่ §6 แยก `synopsis` ออกจาก `hook` เป็นสองฟิลด์ และมีกฎตรวจห้าม `synopsis` ขึ้นต้นด้วยหรือมี `hook` ซ้ำคำต่อคำ (§6.4 กฎ V7)

**(ค) generator ของ v2 สั่งงานฝั่ง Dev ไว้แล้ว แต่สั่งเกินมติไปสองฟิลด์**

`design/v2/lib.mjs:19` เขียนว่า *"UX 8.2 ระบุให้ Dev เพิ่ม views / tropes[] / releaseDay / freeEps / coinPerEp"* — สี่ตัวแรกรับได้ แต่ **`freeEps` และ `coinPerEp` ต้องไม่เข้าสัญญาข้อมูลนี้** เพราะเป็นของยุคเหรียญที่มติ 22 ต.ค. 2026 ตัดไปแล้ว ตัว Visual เองก็ถอดค่าคงที่พวกนั้นออกจาก rev.2 แล้วตามคอมเมนต์ `design/v2/lib.mjs:38-39` เหลือแต่บรรทัด 19 ที่เป็นข้อความค้าง ผมตัดสินใจไม่รับสองฟิลด์นี้ และใส่กฎตรวจอัตโนมัติไว้กันคนเติมกลับ (§6.4 กฎ V8)

ส่วนที่ generator ชดเชยไว้เองชั่วคราว ทั้งหมดต้องย้ายมาเป็นข้อมูลจริงใน `content.json`:

| สิ่งที่ generator ทำชั่วคราว | ตำแหน่ง | ย้ายไปเป็น |
|---|---|---|
| `views` เป็นสตริงฝังตาย 12 ค่า (`'12.4M'`) | `design/v2/lib.mjs:22-27` | `views` เป็นจำนวนเต็มหรือ `null` (§6.3) |
| `tropes` แมปจาก `hook` ด้วยมือ 3 กลุ่ม รอฝ่ายคอนเทนต์ยืนยัน | `design/v2/lib.mjs:29-36` | `tropes[]` + ทะเบียนแท็ก รอ AIO-20 (§6.5) |
| `releaseDay` ถอดจากข้อความ `status` ด้วยตาราง `DAY` | `design/v2/lib.mjs:41-42` | `status` + `releaseDay` แยกฟิลด์ (§6.2) |
| `cover` คำนวณจาก slug | `design/v2/lib.mjs:44` | `cover` เก็บเป็น path ตรง (§6.3) |

ห้าข้อนี้เป็นมติที่ปิดแล้ว ไม่ใช่ตัวเลือก ผมไม่เสนอทางที่ขัดข้อใดข้อหนึ่ง

| # | ข้อจำกัด | เอกสารนี้เคารพที่ไหน |
|---|---|---|
| 1 | ดูฟรีทุกตอน ไม่มีเหรียญ ไม่มี paywall ไม่มีค่าสมาชิก | §6 ไม่มีฟิลด์ราคา/เหรียญ/ตอนฟรี · กฎ V8 ทำให้ build ล้มถ้ามีคนเติมเข้ามา |
| 2 | ไม่มีบัญชีผู้ชม · ของส่วนตัวอยู่ใน `localStorage` เท่านั้น | §5 แยก admin auth ออกจาก viewer login ชัดเจน · §6.6 ห้าม `following`/`cont` เข้า `content.json` |
| 3 | หน้าที่ให้ Google เก็บ ต้องมีเนื้อหาจริงใน HTML ตั้งแต่ตอนส่ง | §4 ทางเลือกทุกทางเป็น static pre-render · §4.5 เกณฑ์ตรวจว่าไม่ซ้ำรอย `watch/ceo-cold.html:36` |

| 5 | ยอดวิว/คะแนนที่ไม่มีระบบวัดรองรับ ห้ามเข้า structured data | §7 — เงื่อนไขปลดล็อกเขียนเป็นเช็กลิสต์ที่เครื่องตรวจได้ |

## 3. "หลังบ้าน" คืออะไร — รับการตีความ และมีข้อค้านหนึ่งข้อที่อยากให้ถามลูกค้า

### 3.1 รับการตีความว่า = แผงจัดการเนื้อหา (admin/CMS)

**เห็นด้วย** และข้อมูลหนุนชัดกว่าที่คิด ไม่ใช่แค่ "ชื่อตอนซ้ำ" แต่เป็น:

- ชื่อตอนไม่ซ้ำ 32 ชื่อ ต่อ 418 ตอน — ซ้ำเฉลี่ย 13 ครั้ง คนอ่านเจอแน่
- ข้อมูลเดียวกันถูก pre-render ไว้ในหน้า static พร้อม ๆ กับที่ `assets/data.js` ถืออีกชุด แก้ชื่อเรื่องเดียวต้องไล่แก้หลายไฟล์ และไม่มีอะไรรับประกันว่าสองที่ตรงกัน
- บริษัทไม่มีฝ่ายคอนเทนต์ คนที่จะแก้คือคนที่ไม่ได้เขียนโค้ด การให้แก้ `assets/data.js` บรรทัดเดียว 36 KB เป็นทางที่พังแน่

CMS แก้ทั้งสามข้อ และ §6 (สัญญาข้อมูล) คือสิ่งที่แก้ข้อที่สองได้จริง เพราะบังคับให้มีแหล่งความจริงแหล่งเดียว

### 3.2 ข้อค้าน — ขอให้ถามลูกค้าหนึ่งคำถาม ก่อนปิดคำว่า "หลังบ้าน" ที่ CMS

ผมไม่ค้านว่า CMS ผิด ผมค้านว่า **CMS ไม่น่าจะเป็น "หลังบ้าน" ทั้งก้อนที่ลูกค้าคิดไว้** และถ้าเราปิดคำนี้ที่ CMS เงียบ ๆ เราจะส่งของที่ยังดูละครไม่ได้

เหตุผลเป็นรูปธรรม: **เว็บดูละครนี้มีแท็ก `<video` ทั้งรีโป = 0** หน้ารับชมทั้ง 12 หน้าเป็นปกนิ่งกับซับทับภาพ และ `assets/app.js:125` ใช้ `setInterval` เดินแถบเวลาเลียนแบบการเล่น ไม่มีไฟล์มีเดียแม้ไฟล์เดียว ไม่มีที่เก็บ ไม่มี CDN ไม่มี transcode ไม่มีพิกัดค่าแบนด์วิดท์

ถ้าลูกค้าพูดคำว่า "หลังบ้าน" โดยนึกถึง "ที่ที่เอาคลิปขึ้นแล้วคนดูได้" CMS ที่พิมพ์ชื่อตอนสวยจะไม่ตอบโจทย์นั้นเลยแม้แต่ส่วนเดียว และช่องว่างนี้ใหญ่กว่าเรื่องชื่อตอนซ้ำมาก

สิ่งที่ผมขอ ไม่ใช่ให้เปลี่ยนงานนี้ แต่ขอให้ถามลูกค้าหนึ่งคำถามว่า **"ตอนนี้คลิปละครอยู่ที่ไหน และใครจะเอาขึ้น"** แล้วได้คำตอบมาสามทาง:

- ถ้าลูกค้าตอบว่า "ยังไม่มีคลิป ขอจัดระเบียบข้อมูลก่อน" → ADR-001 นี้ครบ เดินต่อได้ทันที ไม่ต้องแก้อะไร
- ถ้าตอบว่า "มีคลิปอยู่แล้ว/จะมี" → ต้องมี **ADR-002 ว่าด้วยมีเดียและการส่งวิดีโอ** แยกฉบับ เพราะมันมีค่าแบนด์วิดท์ต่อเดือนที่ขึ้นกับจำนวนคนดู คนละแบบกับ §4.4 ที่เป็นค่าคงที่ และเรื่องเงินเป็นของลูกค้า
- ถ้าตอบว่า "ฝากไว้ YouTube/ผู้ให้บริการอื่น" → ยังต้องมี ADR-002 แต่เล็กกว่ามาก และ `content.json` จะต้องเพิ่มฟิลด์อ้างอิงวิดีโอ ซึ่ง §6.7 เตรียมที่ว่างไว้แล้วแบบไม่ต้องแก้สัญญาย้อนหลัง

**เอกสารนี้จึงประกาศขอบเขตตัวเองว่า: ADR-001 ครอบคลุมแผงจัดการเนื้อหาและเส้นทางเผยแพร่ข้อความ/ข้อมูล ไม่ครอบคลุมการเก็บและส่งไฟล์วิดีโอ** ใครอ่านเอกสารนี้แล้วคิดว่างานหลังบ้านจบ จะเข้าใจผิด

### 3.3 คำตอบที่ได้ — ปิดข้อค้าน §3.2 แล้ว

คำถามใน §3.2 ถูกถามผ่านการ์ดคำถามบน AIO-21 และ **ลูกค้าตอบแล้วเมื่อ 22 ต.ค. 2026 21:34 UTC (23 ต.ค. เวลาไทย)** ว่า:

> **"ยังไม่มีคลิป ขอจัดระเบียบข้อมูลก่อน"**

ผลตามที่ §3.2 ผูกไว้ล่วงหน้า ไม่ใช่การตีความใหม่หลังรู้คำตอบ:

| | ผล |
|---|---|
| ADR-001 | **ครบตามขอบเขต** ไม่ต้องแก้สาระใด — เอกสารนี้จึงเป็น Accepted |
| ADR-002 (มีเดีย/วิดีโอ) | **ยังไม่ต้องเขียน** · ไม่ใช่ว่าไม่ต้องมีตลอดไป — จะต้องมีในวันที่ลูกค้ามีคลิปจริง และเงื่อนไขนั้นยังอยู่ |
| §6.7 ฟิลด์อ้างอิงวิดีโอใน `episodes[]` | **ยังปิดอยู่** ห้ามเติมโดยถือ ADR-001 เป็นฐาน · เงื่อนไขเดิมคงไว้ทุกตัวอักษร: ต้องมี ADR-002 อนุมัติก่อน |
| §4.5 (ทบทวนทางเลือก C) | ไม่ต้องทบทวน เพราะไม่มีภาระวิดีโอเข้ามา |

**ข้อที่ยังจริงอยู่หลังได้คำตอบ และต้องไม่ถูกลืม:** คำตอบนี้ปิดคำถามว่า "ตอนนี้ต้องทำวิดีโอไหม" (ไม่ต้อง) แต่ไม่ได้เปลี่ยนสภาพของเว็บ — หน้ารับชมยังเป็นปกนิ่งกับซับทับภาพ และ `assets/app.js:125` ยังใช้ `setInterval` เดินแถบเวลาเลียนแบบการเล่นอยู่ ดังนั้นประโยคใน §3.2 ที่ว่า **"ใครอ่านเอกสารนี้แล้วคิดว่างานหลังบ้านจบ จะเข้าใจผิด" ยังมีผล** — "หลังบ้านเสร็จ" ในความหมายของ ADR นี้ = แผงจัดการเนื้อหาและเส้นทางเผยแพร่ข้อมูลเสร็จ ไม่ใช่ "เอาคลิปขึ้นแล้วคนดูได้"

## 4. Stack และที่เก็บข้อมูล — ทางเลือกและเหตุผลที่เลือก

### 4.0 เกณฑ์ตัดสิน

เว็บนี้ไม่มีรายได้จากผู้ชมเลย (มติข้อ 1) เกณฑ์เรียงตามน้ำหนัก:

1. ฝั่งผู้ชมต้องไม่ต้องมีเซิร์ฟเวอร์เปิด 24 ชม. — คนดูโหลด HTML นิ่งจาก CDN เท่านั้น
2. ค่าใช้จ่ายคงที่ต่อเดือนต้องต่ำและคาดเดาได้ ไม่ผูกกับจำนวนคนดู
3. HTML ต้องมีเนื้อหาจริงตอนส่ง (มติข้อ 3)
4. จำนวนชิ้นส่วนที่ต้องดูแลต้องน้อย เพราะทีมเล็กและไม่มีฝ่ายคอนเทนต์
5. ข้อมูลต้องมีประวัติการแก้ ย้อนได้ว่าใครแก้อะไรเมื่อไร

ข้อ 1 ตัด "เว็บแอปที่ render ตอน request" ออกทั้งตระกูลตั้งแต่ต้น ทั้งสามทางข้างล่างจึงเป็น static ฝั่งผู้ชมเหมือนกันหมด ต่างกันแค่ที่ "แผงแก้ข้อมูลอยู่ที่ไหน และข้อมูลนอนอยู่ที่ไหน"

### 4.1 ทางเลือก A — Git เป็นที่เก็บข้อมูล (Git-as-CMS) · **ทางที่เลือก**

`content.json` เป็นไฟล์ในรีโป เป็นแหล่งความจริงแหล่งเดียว แผงจัดการเป็นหน้า static ที่รันในเบราว์เซอร์ของทีมงาน อ่าน `content.json` มาแก้ในฟอร์ม แล้วเขียนกลับเป็น commit ผ่าน Git API ของผู้ให้บริการรีโป การ commit จุด CI ให้ validate แล้ว build HTML ใหม่

- **ฝั่งผู้ชม** — ไฟล์ static บน CDN ไม่มีเซิร์ฟเวอร์
- **ฝั่งแอดมิน** — static page + Git API ไม่มีเซิร์ฟเวอร์เปิดค้าง
- **ที่เก็บข้อมูล** — ไฟล์ JSON ใน git ประวัติการแก้ได้ฟรีจาก git log
- **ข้อดี** — ชิ้นส่วนน้อยที่สุด (ไม่มี DB ไม่มีเซิร์ฟเวอร์) · ประวัติ/ย้อนกลับได้ในตัวด้วย `git revert` · ตรวจรีวิวข้อมูลเหมือนรีวิวโค้ดได้ · ข้อมูล 36 KB อยู่ในขนาดที่ไฟล์เดียวสบาย ๆ
- **ข้อเสีย** — แก้พร้อมกันหลายคนจะชน (รับได้: ทีมไม่มีฝ่ายคอนเทนต์ คนแก้คือหน่วยเดียว) · แก้แล้วเห็นผลช้าเท่าเวลา build ไม่ใช่ทันที · ขนาดไฟล์จะเริ่มอึดถ้าเกินหลักหลาย MB (ไกลมาก จาก 36 KB)

### 4.2 ทางเลือก B — Headless CMS สำเร็จรูป

ใช้บริการ CMS สำเร็จรูปเก็บเนื้อหา ทีมงานแก้ในแผงของผู้ให้บริการ แล้ว webhook จุด CI ให้ดึงข้อมูลออกมาเป็น `content.json` แล้ว build static เหมือนเดิม

- **ข้อดี** — แผงแก้ข้อมูลดีกว่าที่เราเขียนเองแน่นอน · มี role/ประวัติ/preview ให้ฟรี · แก้พร้อมกันหลายคนได้
- **ข้อเสีย** — ข้อมูลจริงไปนอนที่ผู้ให้บริการ เราถือแค่สำเนา ผูกกับเจ้าของบริการ · ต้องมีงาน export ไม่งั้นย้ายออกยาก · มีเพดาน free tier ที่โตแล้วต้องจ่าย · เพิ่มบริการภายนอกหนึ่งเจ้าที่ต้องดูแลบัญชีและกุญแจ

### 4.3 ทางเลือก C — แอดมินของเราเองบนเซิร์ฟเวอร์ + ฐานข้อมูล

Node + ฐานข้อมูลสัมพันธ์บน VPS เล็ก เปิดเฉพาะแผงแอดมิน กด publish แล้วไป build static

- **ข้อดี** — ยืดหยุ่นที่สุด ทำ workflow อะไรก็ได้ · เป็น stack ที่โตไปทำ ADR-002 ต่อได้ตรง ๆ
- **ข้อเสีย** — มีเซิร์ฟเวอร์เปิดค้างให้ดูแล แม้จะเป็นฝั่งแอดมิน · ต้อง backup DB เอง (git ให้ฟรีในทาง A) · ของที่ต้องดูแลเยอะที่สุดและแพงที่สุด เพื่อแลกความยืดหยุ่นที่งานตอนนี้ยังไม่ต้องใช้

### 4.4 ค่าใช้จ่ายต่อเดือน เป็นตัวเลข

ราคาตั้งที่ประกาศสาธารณะ ณ ต.ค. 2026 · แปลงที่ 1 USD ≈ 36 THB · **ตัวเลขนี้ไว้ให้ลูกค้าตัดสินใจ ไม่ใช่ใบสั่งซื้อ และเอกสารนี้ไม่ได้ขอให้ซื้ออะไรทั้งนั้น** (§8)

| | A · Git-as-CMS | B · Headless CMS | C · เซิร์ฟเวอร์ + DB |
|---|---|---|---|
| โฮสต์ไฟล์ static (ฝั่งผู้ชม) | 0 THB — free tier ของ static host | 0 THB | 0 THB |
| ที่เก็บข้อมูล | 0 THB — git repo ที่มีอยู่แล้ว | 0 THB ใน free tier · เกินเพดานเริ่ม ~1,050 THB | ~210 THB (รวมใน VPS) |
| เซิร์ฟเวอร์แอดมิน | 0 THB — ไม่มี | 0 THB — ของผู้ให้บริการ | ~210–430 THB (VPS 1–2 vCPU) |
| CI สำหรับ build | 0 THB — free tier (build ~1–2 นาที ไม่กี่ครั้งต่อวัน) | 0 THB | 0 THB |
| backup | 0 THB — git เป็น backup | 0 THB แต่ต้องเขียน export เอง | ~70–140 THB |
| **รวมกรณีใช้ free tier** | **0 THB/เดือน** | **0 THB/เดือน** | **~280–570 THB/เดือน** |
| **รวมกรณีจ่ายเต็มเมื่อโต** | **~150 THB/เดือน** | **~1,050–1,800 THB/เดือน** | **~570–1,100 THB/เดือน** |

สมมติฐานที่ตัวเลขยืนอยู่บน: 12 เรื่อง 418 ตอน ข้อมูล 36 KB · ปริมาณคนดูยังอยู่ในชั้นฟรีของ static host · **ไม่รวมค่าโดเมนและไม่รวมค่าแบนด์วิดท์วิดีโอ** เพราะยังไม่มีโดเมนในรีโป (ไม่มี `CNAME`) และยังไม่มีไฟล์วิดีโอ (`<video` = 0) ค่าวิดีโอเป็นเรื่องของ ADR-002 ตาม §3.2 และมันไม่คงที่ต่อเดือนแบบตารางนี้

### 4.5 ตัดสินใจ: เลือก A

เลือก **ทางเลือก A — Git-as-CMS** ด้วยเหตุผลเรียงตามน้ำหนัก:

1. **ถูกที่สุดและคาดเดาได้** 0 THB/เดือน และเพดานตอนโตยังอยู่หลักร้อย ไม่ใช่หลักพัน — สำคัญมากเพราะเว็บนี้ไม่มีรายได้จากผู้ชมเลย ทาง B ดูฟรีเท่ากันตอนเริ่ม แต่เพดานของมันสูงกว่า A ราวสิบเท่า
2. **ชิ้นส่วนน้อยที่สุด** ไม่มีเซิร์ฟเวอร์ ไม่มี DB ไม่มีบัญชีผู้ให้บริการเพิ่ม — ตรงกับทีมที่ไม่มีฝ่ายคอนเทนต์และไม่มีคนเฝ้าเซิร์ฟเวอร์
3. **ข้อมูลอยู่กับเรา** แหล่งความจริงคือไฟล์ในรีโปเรา ไม่ใช่สำเนาของข้อมูลที่นอนอยู่ที่คนอื่น ไม่มีงาน export ให้ต้องทำ ไม่มี vendor lock-in
4. **ประวัติและย้อนกลับได้ฟรี** แก้ข้อมูลผิดแล้ว `git revert` ได้ทันที และตอบได้ว่าใครแก้อะไรเมื่อไรจาก git log — ทาง C ต้องสร้างกลไกนี้เองทั้งหมด
5. **ข้อเสียของ A ไม่กัดงานนี้** ข้อเสียหลักคือการแก้พร้อมกันหลายคนจะชน ซึ่งเป็นปัญหาของทีมที่มีฝ่ายคอนเทนต์หลายคน — เราไม่มี ถ้าวันหนึ่งมี ให้ย้ายไป B โดย `content.json` ไม่ต้องเปลี่ยนรูป (ดู §4.6)

เหตุผลที่ **ไม่เลือก B**: จุดแข็งของมันคือแผงที่ดีและการทำงานหลายคน ซึ่งเป็นของที่เรายังไม่ต้องใช้ แต่ราคาที่จ่ายคือข้อมูลจริงย้ายออกไปอยู่นอกมือเรา และผูกกับผู้ให้บริการหนึ่งเจ้า — แพงเกินของที่ได้ ณ ขนาดนี้

เหตุผลที่ **ไม่เลือก C**: แพงที่สุด ของที่ต้องดูแลมากที่สุด และความยืดหยุ่นที่มันให้มาคือความยืดหยุ่นที่งานตอนนี้ยังไม่ต้องใช้ ถ้าคำตอบของลูกค้าใน §3.2 ออกมาว่าต้องทำ ADR-002 เรื่องวิดีโอจริง ทาง C อาจกลับมาน่าสนใจ — **ให้ทบทวนข้อนี้ใหม่ตอนทำ ADR-002 ไม่ใช่ตอนนี้**

### 4.6 สิ่งที่ทำให้การตัดสินใจนี้ย้อนกลับได้

จุดสำคัญที่ทำให้เลือก A ได้อย่างไม่เสี่ยง: **ทั้งสามทางมี `content.json` รูปเดียวกันตาม §6 เป็นจุดส่งของให้ build เหมือนกันหมด** ทาง A เขียนไฟล์ตรง ทาง B ให้ CI ดึงมาแปลงเป็นไฟล์รูปนี้ ทาง C ให้เซิร์ฟเวอร์ export มาเป็นไฟล์รูปนี้ แปลว่าถ้าเปลี่ยนใจ **หน้าบ้านไม่ต้องแก้แม้บรรทัดเดียว** เปลี่ยนแค่ของที่อยู่เหนือไฟล์ขึ้นไป นี่คือเหตุผลที่ §6 คือหัวใจของเอกสารนี้ ไม่ใช่ §4

## 5. Admin auth — ต้องมี และไม่ขัดมติตัดล็อกอินผู้ชม

### 5.1 ทำไมสองเรื่องนี้ไม่ใช่เรื่องเดียวกัน

มติข้อ 2 ตัด **บัญชีผู้ชม** ไม่ได้ตัดการยืนยันตัวตนทุกชนิดในระบบ สองอย่างนี้ต่างกันทุกมิติ:

| | viewer login (ตัดถาวร) | admin auth (ต้องมี) |
|---|---|---|
| ใครใช้ | ผู้ชมทั่วไป ไม่จำกัดจำนวน | ทีมงานบริษัท หน่วยเดียว |
| ป้องกันอะไร | — (ไม่มีอะไรต้องป้องกัน เนื้อหาฟรีทั้งหมด) | สิทธิ์ **เขียน** `content.json` |
| กันการอ่านไหม | — | **ไม่กัน** `content.json` และ HTML ทุกไฟล์เป็นของสาธารณะ ใครก็อ่านได้ |
| เก็บข้อมูลส่วนบุคคลของผู้ชมไหม | เคยจะเก็บ จึงถูกตัด | **ไม่เก็บ** เก็บแค่ตัวตนพนักงานผู้แก้ไข |
| อยู่หน้าไหน | ไม่มีอยู่แล้ว | หน้าแอดมินซึ่งไม่อยู่ในเว็บผู้ชม ไม่มีลิงก์จากหน้าผู้ชม ไม่ถูก index |

สรุปเป็นประโยคเดียวที่เอาไปตอบลูกค้าได้: **ผู้ชมไม่ต้องล็อกอินและจะไม่มีวันต้อง เพราะทุกตอนดูฟรีและไม่มีอะไรผูกกับตัวบุคคล · แต่ "คนที่แก้ข้อมูลเว็บได้" ต้องรู้ว่าเป็นใคร ไม่ใช่เพื่อหวงเนื้อหา แต่เพื่อไม่ให้คนนอกมาแก้ชื่อเรื่องหรือลบตอนได้**

ถ้าไม่มี admin auth เลย ใครก็เขียนทับข้อมูลทั้งเว็บได้ — นั่นเป็นปัญหาคนละเรื่องกับมติเรื่องดูฟรีโดยสิ้นเชิง และมติเรื่องดูฟรีไม่ได้พูดถึงมันเลย

### 5.2 กลไกที่เลือก

ยึดตัวตนจากผู้ให้บริการรีโปที่เราใช้อยู่แล้ว (OAuth) และให้สิทธิ์แก้ข้อมูลตามสิทธิ์เขียนรีโปที่คนนั้นมีอยู่จริง

- ไม่มีตารางผู้ใช้ของเราเอง ไม่มีรหัสผ่านที่เราต้องเก็บหรือรีเซ็ต — ลดของที่จะรั่วให้เหลือน้อยที่สุด
- สิทธิ์ผูกกับสิทธิ์รีโปที่มีอยู่แล้ว คนออกจากทีมแล้วถอนสิทธิ์ที่เดียวจบ
- ร่องรอยการแก้ได้ฟรีจาก commit author — ตอบได้ว่าใครแก้อะไรเมื่อไร โดยไม่ต้องเขียน audit log
- **ห้ามใช้รหัสผ่านร่วมกันทั้งทีม** และ **ห้ามฝัง token ของผู้ให้บริการรีโปไว้ในหน้า static ที่ส่งถึงเบราว์เซอร์** สองข้อนี้เป็นข้อห้ามเด็ด ไม่ใช่คำแนะนำ

> **หัวข้อนี้ไม่พอที่จะลงมือทำ — อ่าน §12.1 ต่อ** ย่อหน้าข้างบนบอกว่า "ยึดตัวตนจาก OAuth" แต่ไม่ได้บอกว่า *ใคร* เป็นคนแลก code เป็น token ซึ่งชนกับ §4.1 ที่บอกว่าฝั่งแอดมินไม่มีเซิร์ฟเวอร์ AIO-25 เปิดข้อขัดกันนี้ และ **§12.1 เป็นคำตัดสิน** ห้ามเริ่มงาน auth จาก §5.2 เพียงลำพัง

### 5.3 ประตูที่ต้องผ่านก่อนโค้ดส่วนนี้เข้า main

ผมเป็นคนกำหนดเกณฑ์นี้และกำหนดว่า: **งานตามแผง admin และเส้นทางเขียนข้อมูลตาม §5.2 ต้องผ่านการเซ็นรับของ Security Engineer ก่อน merge** เพราะมันแตะ OAuth token และเปิดเส้นทางเขียนเข้ารีโป อยู่เหนือเกณฑ์ที่ผมตั้งไว้ชัดเจน · และต้องผ่านรีวิวสองฝั่งครบ (Reviewer-Claude + Reviewer-Codex) ไม่เข้าเกณฑ์งานเล็กที่รีวิวฝั่งเดียวได้

ตัวเอกสาร ADR ฉบับนี้เป็นเอกสาร ไม่ใช่โค้ด จึงไม่ต้องผ่านประตูนั้น แต่โค้ดที่เกิดตามมาต้องผ่าน

## 6. สัญญาข้อมูล `content.json` — ส่วนที่สำคัญที่สุดของเอกสารนี้

นี่คือสิ่งเดียวที่ทำให้ Dev-Claude (หน้าบ้าน) กับ Dev-Codex (หลังบ้าน) ทำขนานกันได้โดยไม่ชนกัน

**กฎการใช้สัญญานี้:**

- หลังบ้าน **ผลิต** ไฟล์รูปนี้ · หน้าบ้าน **บริโภค** ไฟล์รูปนี้ · ไม่มีใครเดารูปจากอีกฝั่ง
- ใครอยากเปลี่ยนรูป ต้องแก้ ADR นี้ก่อน ไม่ใช่แก้โค้ดตัวเองแล้วบอกอีกฝั่งทีหลัง
- `assets/data.js` (`window.LAKORN`) ยังอยู่เพื่อให้เว็บเดิมและ `design/v2/` รันได้ **แต่หมดสถานะแหล่งความจริงทันทีที่ `content.json` มีของจริง** — `design/v2/` อ่าน tuple แบบเดิมและ **ห้ามแก้** (Visual เป็นเจ้าของ) ให้ `design/v2/` คงที่ไว้ ไม่ต้องตามสัญญานี้
- ที่ตั้งไฟล์: `content.json` ที่ราก · เป็น UTF-8 · ไม่ต้องสนใจลำดับคีย์

### 6.1 โครงบนสุด

```json

  "genres": [ { "slug": "revenge", "label": "แก้แค้น" } ],
```

| ฟิลด์ | ชนิด | กฎ |
|---|---|---|
| `version` | integer | ขึ้นต้นที่ `1` · ขยับเมื่อเปลี่ยนรูปแบบที่ทำให้ของเก่าอ่านไม่ได้ · หน้าบ้านต้องเช็กและล้มเสียงดังถ้าเจอเลขที่ไม่รู้จัก ไม่ใช่เดาต่อ |

#### 6.3.1 ทำไมแยก `status` ออกเป็นสองฟิลด์

วันนี้ `status` เก็บข้อความไทย 5 แบบ และมันปนสองเรื่องไว้ในฟิลด์เดียว: เรื่องจบหรือยัง กับ ตอนใหม่มาวันไหน พอปนกัน `design/v2/lib.mjs:41-42` จึงต้องมีตาราง `DAY` มาถอดวันออกจากข้อความ ซึ่งแปลว่าถ้ามีคนพิมพ์ข้อความใหม่ที่ไม่อยู่ในตาราง `releaseDay` จะกลายเป็น `null` เงียบ ๆ โดยไม่มีใครรู้

แยกเป็นสองฟิลด์แล้วข้อความไทยที่แสดงกลายเป็นของหน้าบ้านที่ประกอบขึ้นเอง ไม่ใช่ข้อมูลที่ต้องถอดกลับ ตารางย้ายของทั้ง 5 ค่าที่มีอยู่จริง ให้ Dev-Codex ใช้ตอน migrate:

| `status` เดิมใน `assets/data.js` | → `status` | → `releaseDay` |
|---|---|---|
| `"ตอนใหม่ทุกวัน"` | `"ongoing"` | `"daily"` |
| `"ตอนใหม่ทุกอังคาร"` | `"ongoing"` | `"tue"` |
| `"ตอนใหม่ทุกศุกร์"` | `"ongoing"` | `"fri"` |
| `"ตอนใหม่ทุกเสาร์"` | `"ongoing"` | `"sat"` |
| `"จบแล้ว"` | `"ended"` | `null` |

หมายเหตุให้หน้าบ้าน: ป้าย "ใหม่" วันนี้ขึ้นเมื่อ `status === 'ตอนใหม่ทุกวัน'` (`design/v2/lib.mjs:180`) หลังย้ายแล้วเงื่อนไขเดียวกันคือ `releaseDay === 'daily'`

**และอาการที่ย่อหน้านี้เตือนไว้ ตอนนี้มีตัวจริงอยู่ในรีโปแล้ว — ผมตรวจไฟล์เอง (23 ต.ค. 2026):** อะแดปเตอร์ของ generator ที่ `build/content.mjs:34` แปลง `releaseDay` ของสัญญากลับเป็น**ข้อความไทย** (`'ตอนใหม่ทุก' + DAY_TH[...]`) แล้ว `build/content.mjs:99-100` ถอดวันออกจากข้อความนั้นอีกที ด้วยตาราง `DAY` ที่มีแค่ 4 คีย์ (`ทุกวัน` `ศุกร์` `เสาร์` `อังคาร`) — ขาด `จันทร์` `พุธ` `พฤหัสบดี` `อาทิตย์` ซึ่ง `DAY_TH` สร้างได้ ⇒ เรื่องที่ `status:"ongoing"` + `releaseDay:"wed"` **ผ่าน V5 แต่ `releaseDay(s)` คืน `null` เงียบ ๆ** แล้วไปโผล่ใต้หัวข้อ `"จบแล้ว ไม่มีตอนใหม่"` ที่ `build/pages-discovery.mjs:417-418` และหลุดจาก CollectionPage ของหน้าตารางด้วย (`:401` ใช้แค่ `daily`+`weekly`)

วันนี้ยังไม่ระเบิดเพราะข้อมูลจริงมีแค่ 4 ค่าตามตารางข้างบน **มันจะระเบิดวันแรกที่มีคนในแผง admin เลือกวันพุธ** — ซึ่งคือเหตุผลที่สัญญานี้เก็บ `releaseDay` เป็น enum ตั้งแต่ต้น ทางแก้จึงไม่ใช่เติมคีย์ลงตาราง `DAY` แต่คือ **ส่ง `releaseDay` ของสัญญาผ่านอะแดปเตอร์ตรง ๆ ไม่ต้องถอดจากข้อความไทยอีก** (เป็นงานของ Dev-Claude เจ้าของ `build/` ไม่ใช่การแก้สัญญา)

#### 6.3.2 หนึ่งตอน (`episodes[]`) และธงล็อกที่ต้องหายไป

```json
{ "n": 1, "title": "คืนพายุที่สวนก้าน", "durationSec": 166 }
```

| ฟิลด์ | ชนิด | กฎ |
|---|---|---|
| `n` | integer | ✅ เริ่มที่ 1 · เรียงขึ้นต่อเนื่องไม่ข้ามเลข ไม่ซ้ำ · `n` สุดท้ายต้องเท่ากับ `eps` (กฎ V4) |
| `title` | string | ✅ 1–80 ตัวอักษร ตัดช่องว่างแล้วไม่ว่าง |
| `durationSec` | integer | ✅ **จำนวนวินาที ไม่ใช่สตริง `"m:ss"`** · ช่วงที่รับ 30–600 (ของจริงวันนี้อยู่ที่ 85–194 วินาที) · การจัดรูปเป็น "2:46" เป็นหน้าที่หน้าบ้าน |

**ธงล็อกตอนต้องหายไปจากสัญญานี้ ไม่มีฟิลด์ใดแทนมัน** ตามมติดูฟรีทุกตอน

เรื่องที่ Dev-Codex ต้องระวังตอน migrate และผมย้ำเพราะอ่านผิดได้ง่ายมาก: tuple เดิมคือ `[ชื่อ, "m:ss", ธง]` และ **ธงตัวที่สามหมายถึง "ดูได้" ไม่ใช่ "ล็อก"** — `assets/app.js:118` ใส่คลาส `lock` เมื่อ `x[2]` เป็น**เท็จ** และ `assets/app.js:123` เด้ง `'ตอนนี้สำหรับสมาชิก'` เมื่อ `!s.episodes[ep-1][2]` นับจริงคือ `true` 120 ตอน `false` **298 ตอน** แปลว่าวันนี้ล็อกอยู่ 298 ตอน

เพราะ migration ที่ถูกต้องคือ **ทิ้งช่องที่สามไปทั้งหมด** ไม่ใช่แปลงมันเป็นอะไร ทิศของธงจึงไม่ควรมีผลต่อผลลัพธ์เลย — ผมเขียนไว้เพื่อให้ถ้าใครเผลอคิดจะ "เก็บไว้ก่อน" จะได้รู้ว่าค่าที่เก็บไว้มันกลับทิศจากชื่อที่เดา และ 298 ตอนที่ยังล็อกอยู่คือเหตุผลที่ต้องทิ้ง

| V9 | ห้ามมีคีย์ `following` หรือ `cont` หรืออะไรที่เป็นสถานะของผู้ชมรายคน | บังคับมติข้อ 2 ดู §6.6 |
| V10 | `views` ต้องเป็น integer หรือ `null` ห้ามเป็นสตริง · และถ้า `meta.viewsSource === "none"` ทุก `views` ต้องเป็น `null` | กันตัวเลขปลอมแบบ `'12.4M'` กลายเป็นข้อมูลจริง ดู §7 |
| V11 | ทุกเรื่องใน `series[]` ต้องมีไฟล์ HTML ที่ build ออกมาแล้วมี `title` และ `synopsis` อยู่ใน HTML ตอนส่ง | บังคับมติข้อ 3 ดู §6.8 |
| V12 | ถ้า `meta.viewsSource === "none"` ⇒ HTML ที่ build ออกมา **ห้ามมีตัวเลขยอดวิว** และ **ห้ามมีป้าย "วิว" ที่ไม่มีตัวเลข** ดู §12.3 | กันตัวเลขตัวอย่างถูกฝังกลับเข้าโค้ด และกันป้ายกำพร้า " วิว" ที่เกิดจาก `views: null` (§12.2 ตารางรอยต่อ) |
| V13 | ถ้า `meta.viewsSource === "none"` ⇒ ห้ามมีข้อความ **อ้างว่ามีการวัด** (อันดับจากยอดวิว · คนดูมากที่สุด · ยอดนิยมสัปดาห์นี้) ใน `<title>` `meta description` หรือ JSON-LD ดู §12.3 | มติข้อ 5 ห้ามส่งยอดวิวที่ไม่มีระบบวัดให้บุคคลที่สาม — ประโยคที่อ้างการจัดอันดับก็คือการอ้างยอดวิว แค่ไม่มีตัวเลข · ของจริงวันนี้หลุดอยู่ที่ `build/pages-discovery.mjs:348-350` |

### 6.5 `tropes[]` กับการพึ่ง AIO-20

*(ย่อหน้านี้เขียนตอน 23 ต.ค. เช้า ก่อน AIO-20 ปิด — สภาพล่าสุดอยู่ท้ายหัวข้อ)* ตอนนั้นแท็ก trope ยังไม่มีในข้อมูล สิ่งที่มีคือ 3 กลุ่มที่ `design/v2/lib.mjs:29-36` แมปจาก `hook` ด้วยมือ และคอมเมนต์ในไฟล์เองก็เขียนว่ารอฝ่ายคอนเทนต์ยืนยัน

**สัญญานี้ไม่รอ AIO-20** เพื่อไม่ให้งานหลังบ้านค้าง วิธีคือ:

1. ฟิลด์ `tropes[]` และทะเบียน `tropes` **มีอยู่ในสัญญาตั้งแต่วันแรก** แต่ยอมให้เป็น `[]` และทะเบียนว่างได้
2. หน้าบ้านต้องรับ `tropes: []` ได้โดยไม่พัง — ไม่มีแท็กก็ไม่โชว์แถวแท็ก ไม่ใช่โชว์แถวเปล่า
3. เมื่อ AIO-20 ยืนยันชื่อแล้ว เติมทะเบียนและเติมค่าในแต่ละเรื่อง **ไม่ต้องแก้สัญญา ไม่ต้องแก้หน้าบ้าน**
4. **ห้ามเอาการแมป trope ไปฝังในโค้ดแอป** แบบที่ `design/v2/lib.mjs:29-36` ทำ (ซึ่งถูกต้องสำหรับม็อกอัพ แต่ผิดสำหรับของจริง) trope ต้องมาจากข้อมูลเท่านั้น
5. ค่า 3 กลุ่มที่ Visual เดาไว้ (`revenge-karma`, `hidden-identity`, `reborn`) **ถือเป็นข้อเสนอ ไม่ใช่ของที่ยืนยันแล้ว** ให้ AIO-20 เป็นคนตัดสิน

**อัปเดต 23 ต.ค. 2026 — AIO-20 ปิดแล้ว และค่าลงข้อมูลจริงแล้ว** ผมตรวจ `assets/data.js` เอง: ทะเบียน `tropes` มี **13 slug** (`revenge-karma` `comeback` `inheritance` `fruit-drama` `hidden-identity` `ghost` `cross-class-love` `boss-secretary` `reborn-novel` `period` `forbidden-love` `bullied` `murder-mystery`) และทั้ง **12/12 เรื่องมี `tropes` ไม่ว่าง** (0 เรื่องที่ยังว่าง) ⇒ ข้อ 3 ข้างบนเกิดขึ้นแล้วตามที่วางไว้ และข้อ 5 จบ: `reborn` ที่ Visual เดา กลายเป็น `reborn-novel` ในของจริง ซึ่งเป็นเหตุผลที่สัญญาไม่ยอมให้ฝังการแมปไว้ในโค้ด (ข้อ 4)

เหลือสิ่งเดียวที่ยังต้องทำกับ trope คือ **ย้ายค่าพวกนี้เข้า `content.json` ตอน migrate** พร้อมกฎ V3 (ทุกค่าต้องมีในทะเบียน) — ไม่ใช่การรอใครอีกแล้ว

### 6.6 ของที่ "ห้าม" อยู่ใน `content.json`

ข้อนี้สำคัญเท่ากับรายการฟิลด์ที่ต้องมี

`assets/data.js` วันนี้มีคีย์บนสุด 5 ตัว: `genres`, `subs`, `series`, `following`, `cont` — **สองตัวท้ายไม่ใช่ข้อมูลของเว็บ** `following` คือรายการเรื่องที่ผู้ชมติดตาม (5 เรื่อง) และ `cont` คือตอนที่ดูค้างไว้ (4 เรื่อง) มันถูก ship มาเป็นข้อมูลตัวอย่างสำหรับม็อกอัพ ซึ่งถูกต้องสำหรับม็อกอัพ แต่ถ้ามันหลุดเข้า `content.json` จะกลายเป็น "ทุกคนที่เปิดเว็บเห็นว่าตัวเองติดตาม 5 เรื่องเดียวกัน" และแย่กว่านั้นคือเป็นก้าวแรกของการมีบัญชีผู้ชม ซึ่งมติข้อ 2 ตัดถาวร

| ห้ามมี | เพราะ | ที่ถูกต้องคือ |
|---|---|---|
| `following` · `cont` · ประวัติการดู · ความคืบหน้าในตอน | เป็นของรายคน · มติข้อ 2 | `localStorage` ของเบราว์เซอร์ผู้ชมเท่านั้น |
| อะไรที่ระบุตัวบุคคลของผู้ชมได้ (ชื่อ อีเมล id อุปกรณ์) | ไม่มีบัญชีผู้ชม จึงไม่มีเหตุให้เก็บ | ไม่เก็บเลย |
| `freeEps` · `coinPerEp` · ธงล็อก · ราคา · ชั้นสมาชิก | มติข้อ 1 · กฎ V8 | ไม่มี |
| `subs` (ซับตัวอย่าง) | ไม่มีไฟล์วิดีโอให้ซับเกาะ (`<video` = 0) ใส่ไปตอนนี้คือข้อมูลที่ไม่มีความหมาย | เก็บไว้พิจารณาใน ADR-002 ตาม §3.2 |
| ข้อความที่ประกอบขึ้นได้จากฟิลด์อื่น เช่น "24 ตอน" "ตอนใหม่ทุกศุกร์" "12.4M วิว" | ข้อมูลซ้ำสองที่ = เดี๋ยวก็ไม่ตรงกัน ซึ่งเป็นปัญหาเดิมที่เรากำลังแก้ | หน้าบ้านประกอบจาก `eps` `releaseDay` `views` |

### 6.7 ที่ว่างสำหรับวิดีโอ — เตรียมไว้แต่ยังไม่เปิด

ตาม §3.2 ถ้าคำตอบลูกค้าออกมาว่ามีคลิปจริง `content.json` จะต้องอ้างถึงไฟล์วิดีโอได้ ผมจึงล็อกไว้ล่วงหน้าว่าตอนนั้นให้เพิ่มเป็น **ฟิลด์ไม่บังคับใน `episodes[]`** (ไม่ใช่โครงใหม่ ไม่ใช่ขยับ `version`) เพื่อให้ของที่ Dev เขียนวันนี้ไม่ต้องรื้อ

เงื่อนไขของการเติม: **ต้องมี ADR-002 อนุมัติก่อน** เพราะมันมีค่าแบนด์วิดท์ต่อเดือนที่ขึ้นกับจำนวนคนดู และเรื่องเงินเป็นของลูกค้า — ห้ามเติมฟิลด์วิดีโอเข้ามาโดยถือ ADR-001 เป็นฐาน

### 6.8 เส้นแบ่งหน้าที่ระหว่าง Dev-Codex กับ Dev-Claude

| | Dev-Codex (หลังบ้าน) | Dev-Claude (หน้าบ้าน) |
|---|---|---|
| `content.json` | **ผลิต** | **อ่าน ห้ามเขียน** |
| ตัวตรวจ V1–V11 | เจ้าของ | รันได้ แต่ไม่ใช่เจ้าของ |
| migrate จาก `assets/data.js` | เจ้าของ (รวมการทิ้งธงล็อก 298/418 ตาม §6.3.2) | — |
| เขียน `synopsis` ใหม่ 12 เรื่อง | เจ้าของเครื่องมือที่ให้พิมพ์ | — |
| จัดรูป `durationSec` → "2:46" | — | เจ้าของ |
| ย่อ `views` → "12.4M" | — | เจ้าของ |
| ประกอบข้อความ `status`+`releaseDay` → "ตอนใหม่ทุกศุกร์" | — | เจ้าของ |

**หมายเหตุบังคับสำหรับ Dev-Claude** — มติข้อ 3 เกิดจากของจริงที่ยังอยู่ในรีโป: `watch/*.html` ทั้ง 12/12 ไฟล์มี `<h1 id="epTitle"></h1>` ว่างใน HTML (`watch/ceo-cold.html:36`) แล้วให้ JS เติมตอนรัน (`assets/app.js:111`) ห้ามทำซ้ำรูปแบบนี้ เกณฑ์ตรวจง่าย ๆ ที่ใช้ได้เลย: **ปิด JavaScript แล้วเปิดไฟล์ HTML ที่ build ออกมา ต้องอ่านชื่อเรื่อง ชื่อตอน และเรื่องย่อได้ครบ**

สังเกตว่าวันนี้ยังไม่มี JSON-LD ในรีโปเลย (0 ไฟล์) — structured data ทั้งหมดเป็นของใหม่ที่ Dev-Claude จะเขียน ไม่มีของเก่าให้แก้ ดังนั้น §7 เป็นกฎที่บังคับได้ตั้งแต่บรรทัดแรก ไม่ใช่การตามเก็บ

## 7. `views` กับ structured data — ห้ามเมื่อไร ปลดเมื่อไร

### 7.1 สภาพวันนี้: ห้าม

*(ประโยคแรกของย่อหน้านี้ล้าสมัยแล้ว — วันนี้ `assets/data.js` มี `views` เป็นสตริงไทย 12/12 เรื่อง ดู §12.4 · ข้อห้ามทั้งหมดในหัวข้อนี้ยังมีผลทุกตัวอักษร และ **เข้มขึ้น** ตามกฎ V12–V13 ใน §12.3)*

`views` ไม่มีอยู่ใน `assets/data.js` เลย (0/12 เรื่อง) ตัวเลขที่เห็นในม็อกอัพที่อนุมัติมาจากสตริง 12 ค่าที่ฝังไว้ที่ `design/v2/lib.mjs:22-27` และคอมเมนต์ที่ `design/v2/lib.mjs:18-21` ก็เขียนตรง ๆ ว่าเป็นตัวเลขตัวอย่าง ไม่มีระบบวัดอยู่จริงแม้แต่ชิ้นเดียว

ดังนั้นตามมติข้อ 5:

- **โชว์ในหน้าได้** ตามแบบที่อนุมัติ และหน้าที่โชว์ต้องมีหมายเหตุกำกับว่าเป็นตัวเลขตัวอย่าง ตามที่ `design/v2/lib.mjs:20-21` กำหนดไว้แล้ว
- **ห้ามเข้า structured data ที่ส่งให้ Google** เด็ดขาด — ห้ามใส่ `interactionStatistic` / `InteractionCounter` / `aggregateRating` / `ratingValue` / `reviewCount` หรือฟิลด์ทำนองเดียวกันใน JSON-LD
- ค่าในไฟล์ต้องเป็น `null` ไม่ใช่ตัวเลขเดา และ `meta.viewsSource` ต้องเป็น `"none"` (กฎ V10 บังคับให้สองอย่างนี้ตรงกันเสมอ)

เหตุผลที่เข้มข้อนี้: ตัวเลขที่ส่งให้ Google คือการยืนยันข้อเท็จจริงต่อบุคคลที่สาม ส่งตัวเลขที่ไม่มีระบบวัดรองรับคือการให้ข้อมูลเท็จ และโทษของมันตกที่เว็บของลูกค้า ไม่ใช่ตกที่เรา

### 7.2 เงื่อนไขปลดล็อก — ต้องครบทุกข้อ ขาดข้อเดียวคือยังห้าม

ข้อห้ามนี้ปลดเฉพาะฟิลด์ที่วัดจริง ไม่ได้ปลดทั้งหมวด เงื่อนไขเขียนให้เครื่องตรวจได้:

1. มีตัวนับที่ทำงานอยู่จริงบนระบบที่ให้บริการจริง ไม่ใช่ตัวเลขที่คนพิมพ์
2. มีเอกสารกำกับว่า "หนึ่งวิว" นับอย่างไร (นับเมื่อไหร่ · กัน bot อย่างไร · คนเดิมดูซ้ำนับไหม · นับรวมช่วงเวลาไหน) — ถ้าตอบไม่ได้ว่านับอย่างไร ก็ยังไม่เรียกว่าวัดจริง
3. ค่าใน `content.json` ไหลมาจากตัวนับนั้นโดยอัตโนมัติ ไม่มีมือคนแตะกลางทาง
4. `meta.viewsSource` เปลี่ยนเป็น `"analytics"` และ **ตัวตรวจ V10 ต้องผ่าน** คือไม่มี `views` ที่เป็น `null` ค้างอยู่
5. มีเวลาที่วัดกำกับอยู่ด้วย เพื่อให้รู้ว่าตัวเลขเก่าแค่ไหน
6. CTO บันทึกการปลดใน ADR นี้เป็นการแก้ไขที่มีวันที่ **การปลดไม่เกิดเองจากการที่โค้ดพร้อม**

ครบหกข้อแล้ว **`views` เข้า JSON-LD ได้เฉพาะฟิลด์ `views` ตัวเดียว** — `aggregateRating` และคะแนนรีวิวทุกชนิด **ยังห้ามอยู่** เพราะเว็บนี้ไม่มีระบบรับคะแนนจากผู้ชมเลย และจะไม่มี เพราะไม่มีบัญชีผู้ชม (มติข้อ 2) การปลดข้อหนึ่งไม่ลากข้ออื่นตามไปด้วย

### 7.3 สิ่งที่ยังใส่ structured data ได้วันนี้

ข้อห้ามจำกัดอยู่ที่ตัวเลขที่ไม่มีระบบวัด ไม่ได้ห้าม structured data ทั้งหมด ข้อมูลที่เป็นข้อเท็จจริงจากข้อมูลจริงใส่ได้: ชื่อเรื่อง · เรื่องย่อ · จำนวนตอน · แนว · ตอนและชื่อตอน · ความยาวตอนจาก `durationSec` · ภาพปก ทั้งหมดนี้ตรวจย้อนได้จาก `content.json` จึงไม่ใช่การกล่าวอ้างลอย ๆ

## 8. ขอบเขตปฏิบัติการ: เอกสารนี้ไม่ deploy ไม่ตั้งโดเมน ไม่ซื้ออะไร

ตามมติข้อ 4 เอกสารนี้**ไม่มีคำสั่งปฏิบัติการใด ๆ** ไม่มีคำสั่ง deploy ไม่มีการตั้งโดเมน ไม่มีการจัดซื้อ ตัวเลขใน §4.4 เป็นราคาตั้งสาธารณะเพื่อให้ลูกค้าเปรียบเทียบทางเลือกได้ ไม่ใช่การเลือกผู้ให้บริการและไม่ใช่การขออนุมัติงบ เรื่องเงินเป็นของลูกค้า

เส้นที่เอกสารนี้หยุด: **ADR-001 จบลงที่ "มีไฟล์ HTML ที่ build ออกมาถูกต้องและผ่านตัวตรวจ V1–V11"** การเอาไฟล์นั้นขึ้นที่ไหนเป็นงานของ DevOps และอยู่นอกเอกสารนี้

และเพื่อให้คนอ่านไม่เข้าใจผิดว่า §9 คือใบเบิกทางขึ้นของจริง ขอบันทึกสภาพจริงไว้:

- การที่ผมอนุมัติให้ merge **ไม่ใช่การอนุมัติให้ deploy** เป็นสองประตูแยกกัน
- DevOps ขึ้น **staging** ได้เองไม่ต้องขอ · ขึ้น **production** ต้องได้อนุมัติจาก CEO หรือบอร์ดก่อน ทุกครั้งต่อหนึ่งการขึ้น
- **บันทึกมติบอร์ด 22 ต.ค. 2026:** บอร์ดให้ EX-001 และ EX-002 **หมดอายุ** วันที่ 5 พ.ย. 2026 โดยไม่ทำการย้ายไปบัญชีแยกให้จบ และยืนยันว่าการปลดการระงับเป็นการกระทำของบอร์ดเอง ผลคือ **ตั้งแต่ 6 พ.ย. 2026 บริษัทไม่มีเส้นทางเข้าสู่ production ที่ถูกระเบียบ** และการระงับ production session ยังมีผลอยู่ ข้อนี้บันทึกไว้ในฐานะมติของบอร์ดที่มีวันที่ ไม่ใช่การร่างกฎของผมเอง และเอกสารนี้ไม่ได้ขอต่ออายุหรือขอข้อยกเว้นสืบทอดใด ๆ
- ผลต่องานนี้ตรงไปตรงมา: **การวางแผนและทำงานตาม ADR นี้เดินได้ปกติ** เพราะงานทั้งหมดจบที่ build artifact การขึ้น production เป็นเรื่องที่บอร์ดถือไว้ และไม่ใช่สิ่งที่ ADR นี้ต้องหาทางออกให้

### 9.1 เส้นทาง


### 9.2 ใครรัน และเมื่อไร

| คำถาม | คำตอบ |
|---|---|
| ใครกดให้เริ่ม | ทีมงานที่แก้ข้อมูล โดยการบันทึกในแผง admin ไม่มีใครต้องรันคำสั่งด้วยมือ |
| ใครรัน rebuild จริง | **CI** ไม่ใช่คน · DevOps เป็นเจ้าของ CI |
| เมื่อไร | **อัตโนมัติเมื่อมี commit ที่แตะ `content.json`** ไม่มีตารางเวลา ไม่ต้องรอใครสั่ง |
| ตรวจ V1–V11 กี่รอบ | สองรอบ — ในแผงเพื่อให้คนแก้รู้ทันที และใน CI เป็นตัวตัดสิน · **รอบใน CI ข้ามไม่ได้** เพราะรอบในเบราว์เซอร์เชื่อถือไม่ได้โดยธรรมชาติ |
| ตรวจไม่ผ่านแล้วอย่างไร | build ล้ม ไม่มี artifact ออกมา ของเดิมที่ให้บริการอยู่ไม่ถูกแตะ |
| ข้อมูลผิดหลุดไปแล้วแก้อย่างไร | `git revert` commit นั้น แล้ว CI build ของเดิมกลับมาเอง — นี่คือข้อได้เปรียบของทางเลือก A ที่ทาง B/C ต้องสร้างเอง |
| ใครอนุมัติให้โค้ด (ไม่ใช่ข้อมูล) เข้า main | CTO · ต้องผ่านรีวิวสองฝั่งครบ และผ่าน Security sign-off สำหรับส่วน §5 ตาม §5.3 |
| การแก้ข้อมูลต้องรีวิวสองฝั่งไหม | **ไม่ต้อง** — รีวิวสองฝั่งคือเกณฑ์สำหรับการเปลี่ยนโค้ด การแก้ชื่อตอนคือการแก้เนื้อหา ตัวตรวจ V1–V11 เป็นประตูของมัน · ถ้าการแก้ข้อมูลครั้งนั้นต้องเปลี่ยน schema ด้วย นั่นคือการเปลี่ยนโค้ด ต้องรีวิวสองฝั่งและต้องแก้ ADR นี้ก่อน |

### 9.3 ลำดับงานที่ปลดล็อกแล้ว ทำขนานกันได้

เมื่อ §6 เป็นสัญญาที่ตกลงแล้ว สองฝั่งเริ่มพร้อมกันได้ทันทีโดยไม่ต้องรอกัน:

- **Dev-Codex เริ่มได้เลย** — ตัวตรวจ V1–V11 · migration จาก `assets/data.js` (ทิ้งธงล็อก · แปลง `"m:ss"` → `durationSec` · แยก `status`/`releaseDay` ตามตารางใน §6.3.1) · แผง admin + auth §5
- **Dev-Claude เริ่มได้เลย** — อ่าน `content.json` ตาม §6 แล้วประกอบ HTML ให้มีเนื้อหาจริงตอนส่ง · เขียน JSON-LD ตาม §7.3 (ไม่มี `views`) · ใช้ไฟล์ `content.json` ตัวอย่างที่ Dev-Codex ส่งให้ก่อนของจริงเสร็จได้
- **งานที่รอของจากคนอื่นจริง ๆ เหลือชิ้นเดียว** — `synopsis` 12 เรื่องที่ต้องมีคนเขียนเนื้อหาใหม่ เพราะวันนี้ไม่มีอยู่เลย (0/12) และ `hook` ใช้แทนไม่ได้ตามกฎ V7 · ค่า `tropes[]` ไม่รออีกแล้ว AIO-20 ปิดและลงข้อมูลครบ 12/12 (§6.5)
- **คำถาม §3.2 ได้คำตอบแล้ว** — "ยังไม่มีคลิป ขอจัดระเบียบข้อมูลก่อน" (§3.3) จึงไม่มีงานวิดีโอเข้าคิว และไม่มีอะไรรออยู่หน้างานทั้งสองฝั่งอีก

### 12.1 ช่องทาง OAuth ของแผง admin — ตัดสิน: **broker ในเครื่อง (ข้อ 1)**

#### ก. หลักฐานที่ผมตรวจเอง 23 ต.ค. 2026 — และมันทำให้ข้อขัดกันแคบกว่าที่คิด

AIO-25 เขียนว่าปัญหาคือ "ต้องใช้ `client_secret` ตอนแลก code" ถูกต้อง แต่ยังไม่ใช่เหตุผลที่แข็งที่สุด ผมยิง `curl` จากเครื่องนี้เองและได้ผลนี้:

| ปลายทาง (ส่ง `Origin:` ไปด้วย) | ผลที่ได้ | แปลว่า |
|---|---|---|
| `POST https://github.com/login/oauth/access_token` | **ไม่มี header `access-control-allow-*` เลย** | เบราว์เซอร์อ่านคำตอบไม่ได้ |
| `POST https://github.com/login/device/code` | **ไม่มี `access-control-allow-*`** | device flow ติดกำแพงเดียวกัน |
| `OPTIONS` preflight บน `/login/oauth/access_token` | `404` และไม่มี `access-control-allow-*` | preflight ไม่ผ่าน จึงไม่ถึงขั้นส่งของจริง |
| `GET https://api.github.com/` | **`access-control-allow-origin: *`** | API ข้อมูล (อ่าน/เขียนไฟล์ในรีโป) เรียกจากเบราว์เซอร์ได้ |

ข้อสรุปที่ต่างจากในการ์ด และสำคัญกว่า: **จุดแลก token ของ `github.com` ไม่เปิด CORS** ฉะนั้น *ไม่มี* flow ไหนที่เบราว์เซอร์ทำได้ — ไม่ใช่เรื่อง PKCE ไม่ใช่เรื่อง device flow ใครจะเสนอ "หา flow ที่ไม่ต้องมี secret แล้วทำในหน้า static" ก็ปิดไปทั้งตระกูลด้วยเหตุนี้ ไม่ต้องเสียเวลาลองซ้ำ **ต้องมีของที่ไม่ใช่เบราว์เซอร์เป็นคนแลก token** นี่คือเหตุที่ข้อ (1) ไม่ใช่แค่ทางที่สะดวก แต่เป็นทางเดียวที่เหลือในขั้นนี้

แถวสุดท้ายของตารางเปิดทางที่ "เบาแต่แย่กว่า" ไว้ด้วย คือให้ broker แลก token แล้วโยน token กลับไปให้เบราว์เซอร์เรียก `api.github.com` ตรง ๆ **ผมปฏิเสธทางนี้** เพราะมันเอา token ที่มีสิทธิ์เขียนไปวางในหน้าเว็บ ซึ่งชน §5.2 ข้อห้ามเด็ดข้อที่สอง และทำให้ XSS หนึ่งจุดกลายเป็นสิทธิ์เขียนรีโป · เงื่อนไขจึงเป็น **token ต้องไม่ออกจาก broker เลย** และแผงต้องไม่เรียก `api.github.com` เอง (ซึ่งทำให้ CSP ที่ `admin/index.html` ตั้งไว้แล้วว่า `default-src 'self'` ยังรัดได้เท่าเดิม ไม่ต้องผ่อน)

#### ข. ทำไมสิ่งนี้ไม่ได้ล้ม §4.1

§4.1 เขียนว่า "static page + Git API **ไม่มีเซิร์ฟเวอร์เปิดค้าง**" และ §4.0 เกณฑ์ข้อ 1 เขียนว่า "**ฝั่งผู้ชม**ต้องไม่ต้องมีเซิร์ฟเวอร์เปิด 24 ชม." สองประโยคนี้ห้าม *เซิร์ฟเวอร์ที่เปิดค้างไว้ให้บริการ* ไม่ได้ห้าม *โปรเซสที่คนแก้ข้อมูลเปิดตอนจะแก้แล้วปิดเมื่อเลิก* broker ตามข้อนี้:

- ไม่อยู่ในเส้นทางของผู้ชมเลย ผู้ชมยังโหลด HTML นิ่งจาก CDN เหมือนเดิม — เกณฑ์ข้อ 1 ไม่ถูกแตะ
- ไม่มีค่าใช้จ่ายต่อเดือน ตาราง §4.4 ช่อง "เซิร์ฟเวอร์แอดมิน = 0 THB" ยังจริง — เกณฑ์ข้อ 2 ไม่ถูกแตะ
- ไม่มีโดเมน ไม่มี public port ไม่มีบัญชีผู้ให้บริการเพิ่ม — เกณฑ์ข้อ 4 ไม่ถูกแตะ
- **และมันไม่ใช่ทางเลือก C** ทาง C คือเซิร์ฟเวอร์ + ฐานข้อมูลที่เปิดค้างและเป็นที่เก็บข้อมูล · broker ไม่เก็บข้อมูลอะไรเลย แหล่งความจริงยังเป็น `content.json` ใน git ตาม §4.5 ถ้าวันหนึ่งเลิกใช้ broker ข้อมูลไม่ได้อยู่ในนั้นให้ต้องย้าย

#### ค. trust boundary ที่ broker ต้องอยู่ข้างใน — Security เซ็นรับตามรายการนี้

เงื่อนไขทุกข้อเป็นข้อบังคับ ไม่ใช่คำแนะนำ ข้อไหนทำไม่ได้ ให้กลับมาที่ผมก่อนเขียนโค้ดต่อ

| # | เงื่อนไข | เหตุ |
|---|---|---|
| B1 | ผูกกับ `127.0.0.1` เท่านั้น ห้าม `0.0.0.0` ห้ามรับจากวงแลน | broker ไม่ใช่บริการของบริษัท ไม่มีใครควรเรียกได้นอกจากเจ้าของเครื่อง |
| B2 | ตรวจ header `Host` ว่าเป็น `127.0.0.1:<port>` และตรวจ `Origin` ให้ตรง ปฏิเสธที่ไม่ตรง | กัน DNS rebinding — เว็บไหนก็ยิง `127.0.0.1` ของผู้ใช้ได้ นี่เป็นความเสี่ยงประจำของเครื่องมือ localhost ไม่ใช่เรื่องสมมติ |
| B3 | ทุกคำขอที่เขียนต้องมี CSRF token ต่อ session ที่ broker ออกให้ | คุกกี้เดียวไม่พอเมื่อผู้ใช้ท่องเว็บอื่นอยู่ด้วย |
| B4 | token ของผู้ให้บริการรีโป **อยู่ในหน่วยความจำของ broker เท่านั้น** ห้ามเขียนลงดิสก์ ห้ามลง log ห้ามส่งให้เบราว์เซอร์ | §5.2 ข้อห้ามเด็ดข้อที่สอง |
| B5 | เบราว์เซอร์ได้แค่ session cookie แบบ `HttpOnly` + `SameSite=Strict` · อายุ session ไม่เกินช่วงที่เปิดแผง · **ปิดโปรเซส = session ตาย** | ไม่มีอะไรค้างให้ขโมยหลังเลิกงาน · หมายเหตุ: บน `http://127.0.0.1` ธง `Secure` และคำนำหน้า `__Host-` ใช้ไม่ได้ จึงต้องพึ่ง B2+B3 ชดเชย — ข้อนี้ Security ต้องดูเป็นพิเศษ |
| B6 | ก่อนเปิดปุ่มบันทึก ต้องถาม API ว่าผู้ใช้คนนั้น **มีสิทธิ์เขียนรีโปจริง** (`permissions.push`) ไม่มีสิทธิ์ = แผงเป็นโหมดอ่าน | ตรงตาม §5.2 ที่ให้สิทธิ์ตามสิทธิ์รีโปที่มีจริง · ตรงกับข้อเสนอของ Dev |
| B7 | เขียนได้เฉพาะ path ใน allowlist: `content.json` และ `assets/covers/<slug>.<ext>` เท่านั้น · ห้าม force push ห้ามลบ branch ห้ามแตะ `.github/` `build/` `assets/*.js` | ถ้า broker เขียนที่ไหนก็ได้ มันก็กลายเป็นช่องรันโค้ดในเว็บจริงผ่าน CI |
| B8 | อัปโหลดปก: จำกัดขนาด ≤ 1 MB · รับเฉพาะ `webp/png/jpg` และ **ตรวจ magic bytes ไม่เชื่อนามสกุล** · ชื่อไฟล์คำนวณจาก `slug` ไม่เอาชื่อที่ผู้ใช้ส่งมา | กันไฟล์ที่ไม่ใช่รูปและกัน path traversal |
| B9 | branch ปลายทางของ broker ต้อง **ไม่ใช่ branch ที่ CI ใช้ publish** จนกว่า Security จะเซ็นรับ | ให้ของที่ยังไม่ผ่านประตูแตะเส้นทางเผยแพร่ไม่ได้ |
| B10 | broker เป็นโค้ดในรีโป ⇒ ต้องผ่าน **รีวิวสองฝั่งครบ + QA + Security sign-off** ตาม §5.3 ก่อน merge | §5.3 คุมอยู่แล้ว ผมไม่ลดเกณฑ์ให้ และไม่เข้าเกณฑ์งานเล็กรีวิวฝั่งเดียว |

#### ง. ข้อห้ามของขั้นนี้

1. **ห้ามฝัง `client_secret` หรือ token ใด ๆ ในบันเดิล static** — เดิมอยู่ใน §5.2 ย้ำเพราะเป็นต้นเรื่องของการ์ดนี้
2. **ห้ามเอา PAT มาแปะในแผงแล้วเก็บใน `localStorage`/`sessionStorage`** — เท่ากับวาง token สิทธิ์เขียนไว้ให้ XSS หยิบ และอายุยาวกว่า session มาก
3. **ห้ามใช้ broker/บริการ auth ของบุคคลที่สามที่โฮสต์ไว้ข้างนอก** — เป็นการเพิ่มผู้ให้บริการ ต้อง deploy และบางทีต้องจ่าย ชนมติข้อ 4 · ถ้าวันหนึ่งจำเป็นจริง ต้องกลับมาแก้ ADR ก่อน ไม่ใช่เริ่มทำแล้วมาเล่าทีหลัง
4. **ห้ามใช้ credential ของ harness/สภาพแวดล้อมรันงาน (เช่นตัวแปร `PAPERCLIP_GITHUB_*`) เป็นช่องทาง auth ของตัวผลิตภัณฑ์** — มันเป็นกุญแจของเครื่องมือภายในที่รันงานเรา ไม่ใช่กุญแจของบริษัทสำหรับแผง admin การเอามาใช้คือการยืมสิทธิ์ข้ามขอบเขตความเชื่อถือ และทำให้ตอบไม่ได้ว่า commit มาจากตัวจริงคนไหนตาม §5.2
5. **ห้ามใช้รหัสผ่านร่วมกันทั้งทีม** — เดิมอยู่ใน §5.2

#### จ. flow ที่ให้ใช้ เรียงตามลำดับที่ต้องลอง

| ลำดับ | flow | สภาพ secret | เงื่อนไข |
|---|---|---|---|
| 1 | **device flow** ของ GitHub App ที่ติดตั้งไว้เฉพาะรีโปนี้ (สิทธิ์ `contents: write` เท่านั้น) | **ไม่มี secret อยู่บนเครื่องใคร** มีแค่ `client_id` ซึ่งเป็นค่าสาธารณะ | ต้องจดทะเบียน App ก่อน (§10 ข้อ 5) · ผมยืนยันแล้วว่า CORS ปิด จึงต้องให้ broker เป็นคนแลก token แต่ **ยังไม่ได้ทดลองวิ่ง flow จริงเพราะยังไม่มี App จดทะเบียน** — Dev-Codex ต้องทดลองแล้วรายงาน |
| 2 | authorization code + PKCE โดย broker ถือ `client_secret` ใน env ของโปรเซส | มี secret · อยู่ได้เฉพาะ **เครื่องเดียวที่กำหนด** ห้ามแจกหลายเครื่อง ห้ามเข้ารีโป ห้ามเข้า log | ใช้ได้เฉพาะเมื่อลำดับ 1 ใช้ไม่ได้จริง และต้องให้ Security ดูเรื่องการเก็บ secret เป็นหัวข้อแยก |
| — | อย่างอื่น | — | **ถ้าทั้งสองทางใช้ไม่ได้ ให้กลับมาที่ผม** ห้ามด้นสดช่องทางที่สาม |

เหตุที่เรียงลำดับนี้: ลำดับ 1 ทำให้ไม่มีความลับของบริษัทวางอยู่บนโน้ตบุ๊กของใครเลย โน้ตบุ๊กหายก็ไม่มีอะไรต้องหมุนกุญแจ และสิทธิ์ของ token ถูกจำกัดที่ installation ของรีโปเดียว ไม่ใช่ทุกรีโปที่คนนั้นเข้าถึงได้ · ลำดับ 2 แลกสองข้อนี้ทิ้งไป จึงเป็นทางสำรอง ไม่ใช่ทางตั้งต้น

#### ฉ. เส้นทางที่ต้องใช้งานได้ตลอด ไม่ว่า broker จะเสร็จหรือไม่

**แผงต้องทำงานได้โดยไม่มี auth เลย** ด้วยเส้นทางที่มีอยู่แล้ววันนี้: แก้ในแผง → กด "ตรวจและส่งออก `content.json`" (`admin/index.html` ปุ่ม `#export`) → คนที่มีสิทธิ์เขียนรีโป commit ไฟล์นั้น → CI ตรวจ V1–V13 แล้ว build ตาม §9.1

เส้นนี้ **ไม่ใช่ของชั่วคราวที่จะถูกถอด** ต้องคงไว้ถาวร เพราะ:

- มันถูกระเบียบแน่นอนที่สุด ไม่มี token ไม่มี session ไม่มีผิวสัมผัสใหม่ จึงไม่ต้องรอ Security sign-off เพื่อใช้ — **AIO-23 เดินต่อได้วันนี้โดยไม่ต้องรอข้อ 12.1 ก–จ เสร็จ**
- มันเป็นทางถอยเมื่อ broker พัง ซึ่ง "คนแก้ข้อมูลทำงานไม่ได้เลยเพราะเครื่องมือภายในพัง" เป็นความเสี่ยงที่เลี่ยงได้ฟรี
- ร่องรอยยังอยู่ครบ ผู้ commit คือผู้รับผิดชอบตาม §5.2 เหมือนกัน

สิ่งที่ broker เพิ่มให้คือความสะดวกของคนที่ไม่ได้เขียนโค้ด (§3.1) **ไม่ใช่ความสามารถใหม่ของระบบ** จัดลำดับงานตามนี้: เส้นส่งออกให้เรียบร้อยก่อน broker มาทีหลัง

#### ช. §12.1 ไม่ได้ให้สิทธิ์อะไรที่เกี่ยวกับ production

เขียนไว้กันอ่านผิด: broker เป็นเครื่องมือบนเครื่องของคนทำงาน **ไม่ใช่เครื่อง production ไม่ใช่ deploy ไม่ใช่ session บนเครื่อง production และไม่ใช่คำขอข้อยกเว้นใด ๆ** การระงับ production session ของบอร์ดยังอยู่ และบันทึกใน §8 เรื่องที่บอร์ดให้ EX-001/EX-002 หมดอายุ 5 พ.ย. 2026 ยังอยู่ครบทุกตัวอักษร เอกสารนี้ไม่ขอต่ออายุและไม่ขอข้อยกเว้นสืบทอด · ปลายทางของงาน AIO-23 ยังเป็น build artifact ตาม §8 เหมือนเดิม

### 12.2 ขอบเขตการนับวิว — ตัดสิน: **เลื่อนตาม §7 ไม่สร้างตัวรับ aggregate ใน AIO-23**

#### ก. คำตัดสินและเหตุผล

AIO-23 **ไม่ต้องทำ** ตัวนับวิว ไม่ต้องทำตัวรับ aggregate ไม่ต้องทำ endpoint รับยอดใด ๆ · seed คงสภาพที่เป็นอยู่: ผมตรวจ `content.json` ที่รากเองวันนี้ — `meta.viewsSource = "none"` และ `views` เป็น `null` ครบ 12/12 เรื่อง ซึ่งถูกต้องตาม §7.1 และกฎ V10 แล้ว **ไม่ต้องแก้อะไร**

เหตุผล เรียงตามน้ำหนัก:

1. **§7.2 ข้อ 1 ยังทำให้ครบไม่ได้ และไม่ใช่เพราะเรายังไม่ลงมือ** เงื่อนไขคือ "ตัวนับที่ทำงานอยู่จริงบน**ระบบที่ให้บริการจริง**" วันนี้เรายังไม่มีเส้นทางขึ้น production ที่ถูกระเบียบ และตามมติบอร์ดใน §8 ตั้งแต่ 6 พ.ย. 2026 จะไม่มีเลย การสร้างตัวรับไว้ก่อนจึงไม่ใช่การเตรียมตัว แต่เป็นการสร้างของที่ไม่มีอะไรป้อนให้ได้ตามระเบียบ
2. **ยังไม่มีคลิป ⇒ คำว่า "หนึ่งวิว" ยังไม่มีสิ่งอ้างอิง** ลูกค้าตอบใน §3.3 ว่ายังไม่มีคลิป และสภาพหน้ารับชมตาม §3.2 ยังเป็นปกนิ่ง ถ้านับตอนนี้ สิ่งที่นับได้คือ "คนเปิดหน้า" ไม่ใช่ "คนดู" การเอาเลขนั้นไปแสดงใต้ไอคอนรูปตาข้างคำว่า "วิว" คือการบอกข้อเท็จจริงผิดแบบเดียวกับที่ §7.1 ห้าม ต่างกันแค่ว่ามันผิดในหน้าเว็บแทนที่จะผิดใน structured data · และ §7.2 ข้อ 2 บังคับให้ตอบได้ว่านับอย่างไร ซึ่งตอบไม่ได้ก่อนรู้ว่ามีอะไรให้ดู
3. **Git-as-CMS ไม่มีที่ให้เขียนยอดวิว และไม่ควรมี** ตามที่การ์ดตั้งข้อสังเกตไว้ถูกต้องแล้ว การเขียนยอดวิวเป็น commit คือ 1 commit ต่อ 1 วิว และจุด CI ทุกครั้ง · ส่วน broker ใน §12.1 เป็นเครื่องมือที่ "คนแก้ข้อมูลเปิดเอง" ไม่ใช่ปลายทางสาธารณะ จะทำให้มันรับยอดจากผู้ชมได้ต้องเปิดมันเป็นบริการ 24 ชม. ซึ่งชนเกณฑ์ §4.0 ข้อ 1 ตรง ๆ และเปิดผิวสัมผัสสาธารณะที่ไม่มี auth
4. **§7.2 ข้อ 3 ห้ามมือคนแตะกลางทาง** ถ้าสร้างตัวรับไว้ตอนนี้ แรงกดดันที่จะ "ใส่เลขไปก่อนให้หน้าดูสมบูรณ์" จะไปตกที่ช่องนั้น ซึ่งเป็นสิ่งเดียวกับที่กฎ V10 ตั้งมาเพื่อกัน

**การเลื่อนนี้ผูกกับ ADR-002 ไม่ได้ลอยอยู่เฉย ๆ** เงื่อนไขปลดคือ: มี ADR-002 (มีเดีย/วิดีโอ) อนุมัติแล้ว **และ** §7.2 ครบทั้งหกข้อ เหตุที่ผูกกับ ADR-002 เพราะนิยาม "หนึ่งวิว" ต้องอ้างอิงการเล่นวิดีโอ ซึ่งเป็นสาระของ ADR-002 ไม่ใช่ของ ADR-001 · นี่คือการใช้เงื่อนไขที่ §3.3 วางไว้แล้ว ไม่ใช่เงื่อนไขใหม่ที่ผมเพิ่งคิด

### 13.1 ต้นเหตุ และของที่ต้องเพิ่มจากที่สั่งมา: ปกไหลผ่าน **สองท่อ** ไม่ใช่ท่อเดียว

แต่ข้อความสั่งงานบอกว่า "ทุกปกในเว็บไหลผ่านจุดเดียวคือ `coverImg()`" — **จริงแค่ครึ่งเดียว** และครึ่งที่ขาดคือครึ่งที่แพงกว่า:

| ท่อ | ตัวช่วย | จุดเรียก | เห็นไฟล์ในดิสก์ไหม |
|---|---|---|---|
| ฝั่ง build (HTML ที่ส่งออก) | `coverImg()` `build/ui.mjs:82` | 12 จุด (บรรทัดที่ขึ้นข้อความ `coverImg(` มี 13 บรรทัด — หนึ่งในนั้นคือบรรทัดนิยามเอง) | **เห็น** — รันบน node |

**ผลต่อสัญญา และนี่คือจุดที่ผมเบนจากที่สั่งมา:** ข้อความสั่งงานบอกให้ใช้โครงของ `shareSlot()` (`build/seo.mjs:53`) ซึ่ง "ส่องโฟลเดอร์ `assets/share/` ตอน build ถ้าไม่เจอก็ถอยไปใช้ปก" โครงนั้นถูกต้องและพิสูจน์แล้วในรีโปนี้ (Visual ส่งไฟล์ครบ 13 ใบแล้ว `assets/share/README.md` และ `build/build.mjs:344` เลิกเตือนไปแล้ว) **แต่มันทำงานได้เฉพาะท่อที่หนึ่ง** — `build/app.src.js:36` รันในเบราว์เซอร์ เรียก `fs.existsSync()` ไม่ได้ ⇒ ถ้าใช้การส่องโฟลเดอร์เป็นกลไก การ์ด "ดูต่อ" จะไม่มีทางรู้ว่ามีไฟล์กว้างอยู่หรือไม่ และจะครอปต่อไปตลอด แม้ Visual ส่งไฟล์ครบ

### 13.2 ฟิลด์ `orientation` — บังคับ และเป็นของระดับเรื่อง

**D1 · บังคับ — รับข้อเสนอของ CEO และนี่คือเหตุผลของผมเอง ไม่ใช่การยอมตาม**

```json
"orientation": "vertical"
```

| | |
|---|---|
| ชนิด | `"vertical"` \| `"horizontal"` — enum สองค่า ไม่มีค่าที่สาม ไม่มี `null` |
| จำเป็น | ✅ **บังคับ** · เข้า `REQUIRED_SERIES` ที่ `build/content.mjs:61` |
| ระดับ | **ของเรื่อง** (`series[]`) ไม่ใช่ของตอน |

เหตุผลที่ต้องบังคับ ไม่ใช่ตั้งค่าตั้งต้นให้:

1. **ค่านี้ไม่ใช่การตกแต่ง มันเลือกกล่องให้วิดีโอ** ถ้าเดาผิด เรื่องแนวนอนทั้งเรื่องจะถูกยัดลงกรอบ 9:16 (`assets/site.css:514`) ได้แถบดำบน-ล่างเกินครึ่งจอ ซึ่งแย่กว่าการครอปวันนี้ · ความเสียหายต่อหนึ่งค่าที่เดาผิด = ทุกตอนของเรื่องนั้น
2. **ไฟล์นี้มีวินัย "หายแล้วล้มดัง" อยู่แล้ว** — `requireFields()` ที่ `build/content.mjs:62-72` โยน error พร้อมชื่อเรื่องและชื่อฟิลด์ และคอมเมนต์ที่ `build/content.mjs:49-59` แยก "ไม่บังคับจริง" ออกจาก "บังคับ" ไว้ชัดแล้ว · ฟิลด์ที่ยอมให้หายในไฟล์นี้มีเกณฑ์เดียวกันหมด คือ **หายแล้ว "ไม่ render ส่วนนั้นเลย"** (`views` → ไม่มีป้าย · `tropes` → ไม่มีชิป) · `orientation` ไม่เข้าเกณฑ์นั้น เพราะหายแล้วไม่มีทาง "ไม่ render เพลเยอร์"
3. **ค่าตั้งต้นที่ถูกวันนี้จะกลายเป็นค่าผิดในวันที่เติมเรื่องแนวนอนเรื่องแรก** และวันนั้นจะไม่มีใครรู้ว่าต้องกลับมาแก้ ซึ่งเป็นอาการเดียวกับที่ §6.3.1 บันทึกไว้ (`releaseDay` กลายเป็น `null` เงียบ ๆ แล้วเรื่องไปโผล่ใต้หัวข้อ "จบแล้ว")
4. **ราคาของการบังคับวันนี้คือ 12 ค่า** ส่วนราคาของการไม่บังคับคือการค้นทั้งเว็บว่าตรงไหนเดาไว้

**D2 · ระดับเรื่อง ไม่ใช่ระดับตอน** — ข้อนี้ CEO ถามตรงว่า "ถ้าเรื่องเดียวมีทั้งตอนแนวตั้งและแนวนอนได้ สัญญาคนละรูป และราคาต่างกันมาก" คำตอบคือ **ระดับเรื่อง** ด้วยสี่เหตุผล:

1. **ผิวที่ใช้ค่านี้เป็นผิวระดับเรื่องทั้งหมด** — ฟีดเลื่อนทีละ **เรื่อง** ไม่ใช่ทีละตอน (`build/pages-discovery.mjs:159` ผูกกล่องด้วย `data-slug` และ `build/app.src.js:873` ใช้ `list = D.series`) · การ์ด "ดูต่อ" และ `.nextup`/`.endcard` ก็หยิบปกของเรื่อง
2. **ถ้าทิศเปลี่ยนกลางเรื่อง กล่องเพลเยอร์จะเปลี่ยนรูประหว่าง EP.3 กับ EP.4** — ผู้ชมที่กดตอนถัดไปจะเห็นหน้าเด้ง และ `.nextup .thumb`/`.endcard .ec-next .thumb` ที่ขึ้นก่อนตอนถัดไปจะกำหนดขนาดล่วงหน้าไม่ได้ ⇒ CLS ที่กันไม่ได้ด้วยการประกาศ `width`/`height`
3. **ราคาในการดูแลข้อมูล** — ระดับเรื่อง 12 ค่า · ระดับตอน 418 ค่า (`eps` รวม `build/build.mjs:342`) และทุกค่าต้องถูกตรวจ ต้องมีช่องในแผง admin ต่อตอน
4. **ทางหนีมีอยู่ และถูกกว่าการทำวันนี้** — ถ้าวันหน้ามีเรื่องที่ตอนพิเศษเป็นแนวนอนจริง ให้เพิ่ม **ฟิลด์ไม่บังคับระดับตอน** ที่ override ค่าของเรื่อง (`episodes[].orientation`) โดยใช้โครงเดียวกับ §6.7 — เพิ่มได้โดยไม่ขยับ `version` และไม่ต้องรื้อของที่เขียนวันนี้ เพราะตัวอ่านจะคิดเป็น `ep.orientation ?? series.orientation` อยู่แล้ว · **ห้ามเพิ่มล่วงหน้า** ตามหลักเดียวกับ §6.7: ฟิลด์ที่ไม่มีของจริงมารองรับคือฟิลด์ที่จะถูกกรอกผิด

**ความต่างที่ต้องไม่สับสน และมีของจริงรออยู่แล้วในรีโป:** ทะเบียน `genres` มีแนวชื่อ `vertical` (`"ละครแนวตั้ง"`) อยู่แล้ว แต่ **แนว ≠ ทิศ** — แนวเป็นหมวดบรรณาธิการ (เรื่องนี้ถูกจัดอยู่หมวดอะไร) ทิศเป็นรูปทรงจริงของไฟล์ · ตรวจของจริงใน `content.json` วันนี้: มีเพียง **5/12 เรื่องที่มีแนว `vertical`** (`ceo-cold` `billion-widow` `villainess-reborn` `undercover-tycoon` `mangosteen-heart`) ขณะที่ปกทั้ง **12/12 ใบเป็น 1024×1536** และยังไม่มีไฟล์วิดีโอในระบบเลย ⇒ ถ้าใครคิดจะอนุมานทิศจากแนวเพื่อประหยัดฟิลด์ **จะได้ผลผิด 7 ใน 12 เรื่องทันทีวันแรก** · ห้ามอนุมานทิศจาก `genres`, จากสัดส่วนไฟล์ปก, หรือจากชื่อ slug

### 13.3 `version` ขยับเป็น 2 — และทางย้ายที่ไม่ทำให้ไฟล์ในมือลูกค้าอ่านไม่ได้

**D3** การเพิ่มฟิลด์บังคับทำให้ไฟล์เก่าอ่านไม่ได้ด้วยตัวอ่านใหม่ และทำให้ไฟล์ใหม่ถูกตัวอ่านเก่า**อ่านผิดแบบเงียบ ๆ** (เรื่องแนวนอนในกรอบ 9:16) — อาการที่สองคือเหตุผลที่ฟิลด์ `version` มีอยู่ตั้งแต่ต้น ("กันข้อมูลรูปใหม่ไหลเข้าโค้ดเก่าเงียบ ๆ" กฎ V1 §6.4) จึงต้องขยับเลข ไม่ใช่เติมฟิลด์เฉย ๆ

| ไฟล์ | `build/` (`KNOWN_VERSIONS` ที่ `build/content.mjs:20`) | ตัวนำเข้าของ `admin/` (`admin/validate.mjs:12`) |
|---|---|---|
| `version: 1` (ไม่มี `orientation`/`coverWide`) | **ปฏิเสธ** — build ล้มพร้อมข้อความว่าต้องเลือกทิศก่อน · เพราะ build ที่ไม่รู้ทิศมีทางเดียวคือเดา ซึ่งข้อนี้ห้าม | **รับ** — เพื่อให้ไฟล์ที่ลูกค้าส่งออกไว้ก่อนหน้านี้ (`admin/editor.mjs:45-46`) ยังเปิดได้ |
| `version: 2` | **รับ** และบังคับ `orientation` ครบทุกเรื่อง (V14) | รับ |

**กฎที่ทำให้ `version: 1` ไม่กลายเป็นประตูหลัง:** ตัวนำเข้ารับไฟล์ v1 ได้ แต่ **ส่งออกเป็น v2 เท่านั้น** และจะส่งออกไม่ผ่านจนกว่าทุกเรื่องจะมีทิศที่ **คนเลือก** — ไม่มีจุดใดในระบบที่เติม `"vertical"` ให้เอง · ในรีโปห้ามมี `content.json` ที่ `version: 1` หลัง commit ที่ย้ายเสร็จ (ด่านเดียวกับ V14)

**ขั้นตอนย้ายของเรา 12 เรื่อง — ต้องอยู่ใน commit เดียว** (วินัยเดียวกับ V10 ที่บังคับว่า `views` ต้องครบทุกเรื่องใน commit เดียวกัน `build/content.mjs:86-88`):

1. เครื่องมือย้ายครั้งเดียวที่เก็บไว้ในรีโปเพื่อให้ตรวจย้อนได้ว่าค่ามาจากไหน ไม่ได้พิมพ์ขึ้นเอง — รูปแบบเดียวกับ `tools/migrate-content-v2.mjs` (ชื่อนั้นหมายถึงรูปแบบของ `assets/data.js` ไม่ใช่ `version` ของสัญญา — ตั้งชื่อใหม่ให้ไม่ชนกัน)
2. ค่าที่เครื่องมือเติมคือ `"vertical"` ทั้ง 12 เรื่อง · **ข้ออ้างที่ทำให้ค่านี้เป็นข้อเท็จจริงไม่ใช่ค่าตั้งต้น:** ปกทั้ง 12 ใบเป็น 1024×1536 (ตรวจด้วย `file assets/covers/*.webp`) · ยังไม่มีไฟล์วิดีโอในรีโปแม้ไฟล์เดียว (`<video` = 0 จุดนอก `design/v2/`) · ตัวสินค้าตามแบบที่ลูกค้าอนุมัติเป็นละครแนวตั้ง · ผมในฐานะ CTO ยืนยันค่านี้ด้วยหลักฐานสามข้อนี้ ไม่ใช่ปล่อยให้โค้ดเดา
3. `version: 1` → `2` ในไฟล์เดียวกัน · `KNOWN_VERSIONS`, `REQUIRED_SERIES`, `admin/validate.mjs` และกฎ V14–V18 เข้าพร้อมกัน (ลำดับบังคับใน §13.8)

**หลักฐานว่าเว็บไม่เปลี่ยนแม้พิกเซลเดียวหลังย้าย:** ทั้ง 12 เรื่องเป็น `vertical` ⇒ กล่องเพลเยอร์ยังได้ 9:16 เท่าเดิม · ฟีดยังมีครบ 12 เรื่องเท่าเดิม · ยังไม่มีไฟล์ใน `assets/covers-wide/` ⇒ ทุกที่วางที่ขอทรงกว้างถอยไปใช้ `cover` ครอปแบบวันนี้ และ `<picture>` ของฮีโร่ยุบเหลือ `<img src=cover>` ซึ่งเป็น HTML ที่ byte เท่าเดิม ⇒ **Dev ลงมือได้ทันทีโดยไม่ต้องรอ Visual** ตามที่สั่งมา

### 13.4 สินทรัพย์ภาพใบที่สอง: `coverWide`

**D4 · D5**

```json
"cover":     "assets/covers/ceo-cold.webp",
"coverWide": "assets/covers-wide/ceo-cold.webp"
```

| | `cover` (ของเดิม) | `coverWide` (ใหม่) |
|---|---|---|
| ทรง / ขนาด | 2:3 · 1024×1536 | **11:5 (2.2) · 2640×1200 เป๊ะ · WebP · ≤300 KB** (เหตุผลของทรงนี้อยู่ย่อหน้าล่าง) |
| จำเป็น | ✅ บังคับเหมือนเดิม — ไม่มีอะไรพังถ้าไม่มีภาพกว้าง | ➖ **ไม่บังคับสำหรับเรื่องแนวตั้ง** · ✅ **บังคับสำหรับเรื่องแนวนอน** (V16) |
| พาธ | `assets/covers/<slug>.<ext>` (กฎเดิม V6 · `admin/validate.mjs:41`) | `assets/covers-wide/<slug>.<ext>` · `ext ∈ {webp,png,jpg,jpeg}` · ของที่ Visual ส่งคือ `.webp` |
| ถ้าไม่มี | build ล้ม (V6) | **ถอยไปใช้ `cover` ครอปแบบวันนี้เป๊ะ** + เตือนตอน build ไม่ล้ม |

**ทำไมเป็นโฟลเดอร์ใหม่ ไม่ใช่โฟลเดอร์เดิม:** `assets/covers/` ผูกไว้กับ "หนึ่งไฟล์ต่อเรื่อง" ในสามที่ที่เป็นโค้ดจริงแล้ว — `admin/covers.mjs:12` คืนพาธ `assets/covers/<slug>.<ext>` จากชื่อ slug ตรง ๆ · `admin/validate.mjs:41` บังคับ regex นั้น · `admin/github.mjs:29` ยอมให้ commit ได้แค่พาธรูปนั้น ⇒ ไฟล์ใบที่สองในโฟลเดอร์เดียวกันจะชนกฎทั้งสามข้อ และจะทำให้ "สองใบของเรื่องเดียว" แยกจากกันด้วยนามสกุลเท่านั้น ซึ่งเป็นกับดัก

**ทำไมเป็นฟิลด์ ไม่ใช่การส่องโฟลเดอร์แบบ `shareSlot()`** — เหตุผลเต็มอยู่ใน §13.1 ย่อสั้น: `build/app.src.js:36` รันในเบราว์เซอร์ จึงเลือกไฟล์จากดิสก์ไม่ได้ · ข้อมูลเดินทางไปถึงเบราว์เซอร์ได้ผ่าน `assets/content.js` (`build/build.mjs:256-259`) · ผลพลอยได้คือกฎถอยกลับเขียนได้เหมือนกันทั้งสองท่อ (`s.coverWide || s.cover`) และตรวจย้อนได้จากข้อมูลว่าเรื่องไหนมีภาพกว้างแล้ว ไม่ต้องรันเพื่อรู้

**ทำไมภาพแชร์ 1200×630 ที่มีอยู่แล้วใช้แทนไม่ได้** — `assets/share/series-<slug>.jpg` ครบ 12 ใบและเป็นแนวนอน แต่มัน **เป็นการ์ดที่มีตัวหนังสือเผาติดอยู่ในภาพ** (สร้างจาก HTML/CSS โดย `design/v2/share-cards.mjs` ตาม `assets/share/README.md`) และมีเพดาน 300 KB ที่จูนไว้ให้ crawler ของ LINE ⇒ เอามาเป็นพื้นฉากฮีโร่จะได้ชื่อเรื่องซ้อนชื่อเรื่อง · แต่ **สายพานการผลิตมีอยู่แล้ว** และนั่นคือทางที่ถูกสำหรับไฟล์ 12 ใบนี้ (งานของ Visual ไม่ใช่ของ Dev ดู §13.10)

**ทำไมเรื่องแนวนอนต้องมี `coverWide` — ผมเพิ่มเงื่อนไขนี้จากที่สั่งมา:** ข้อความสั่งงานบอกว่า `coverWide` ไม่บังคับเฉย ๆ ซึ่งถูกสำหรับวันนี้ที่ทุกเรื่องเป็นแนวตั้ง แต่เรื่อง**แนวนอน**ที่ไม่มีภาพกว้างจะได้สภาพที่แย่ที่สุดในทั้งเอกสารนี้: เพลเยอร์กรอบ 16:9 ที่มีโปสเตอร์ 2:3 อยู่ข้างใน (ครอป) ทุกการ์ดทรงกว้างครอป และภาพแชร์ครอป · ราคาของกฎนี้วันนี้ = **ศูนย์** (0 เรื่องแนวนอน) ราคาของการไม่มีกฎ = จ่ายตอนมีของจริงแล้วแก้ไม่ทัน

**ทรง 11:5 ไม่ใช่ 16:9 — ข้อนี้ผมแก้คำตัดสินของตัวเองหลังเห็นของจริงของ Visual** ร่างแรกของหัวข้อนี้ล็อก 16:9 ไว้ตามคำว่า "ภาพกว้าง 16:9" ในใบงาน · ระหว่างเขียน Visual เริ่ม AIO-56 แล้ว (ตัวสร้าง `design/v2/covers-wide.mjs` · ยังอยู่ใต้ `design/v2/` และรอ ADR นี้ล็อกพาธ) และเลือก **11:5 = 2.2 ที่ 2640×1200** พร้อมเหตุผลที่วัดมา: กล่องฮีโร่ไหลจาก 1.670 ถึง 2.902 ⇒ 2.2 คือค่าที่ทำให้ "ครอปมากสุด" ต่ำที่สุดตลอดช่วง (**≤24.2%**) ขณะที่ 16:9 ครอป 31% ที่ ar 2.6 และ 39% ที่ 1366×768 · ผมตรวจต่อให้ครบว่ามันไม่ทำร้ายช่องอื่น: ช่องเดียวที่ขอทรงกว้างนอกฮีโร่คือ `.cont .thumb` ที่เป็น 16/9 เป๊ะ (`assets/site.css:231`) ไฟล์ 2.2 ในกรอบ 1.778 ถูกครอป**ด้านกว้าง** 19.2% คือข้างละ 9.6% ซึ่งอยู่ในกรอบปลอดภัยที่ตัวสร้างบังคับไว้ (เว้นขอบด้านละ 12.1%) ⇒ **ไฟล์ใบเดียวรับได้ทั้งสองช่อง** จึงรับทรงของ Visual เป็นค่าในสัญญา · 2640 = 1248 CSS px × DPR 2 + เหลือ ⇒ ไม่มีการขยายภาพบนจอ retina

**ของที่ AIO-56 รออยู่ ล็อกแล้วด้วยสองค่านี้** (ตัวสร้างเขียนไว้เองว่ารอ ADR นี้ก่อนจะเปลี่ยนปลายทาง): ปลายทางคือ **`assets/covers-wide/<slug>.webp`** โดยใช้ `slug` ตามสัญญา §6.3 ตรง ๆ ไม่แปลงชื่อ · ไฟล์ที่ย้ายเข้า `assets/` ถือเป็นของ Dev ตามเส้นแบ่งเดิม ⇒ Visual ส่งไฟล์ให้ แล้วคนที่เติมฟิลด์ `coverWide` ลง `content.json` คือฝั่งข้อมูล (Dev-Codex / แผง admin) ไม่ใช่ตัวเรนเดอร์เขียนเอง — ตามหลัก D5 ที่ว่าโฟลเดอร์ไม่ใช่แหล่งความจริง

**ขนาดต้องเป๊ะ ไม่ใช่ "2.2 ประมาณนี้"** เพราะ `width`/`height` ที่ส่งออกไปกับ `<img>` มาจากค่าคงที่ในโค้ด (`COVER_W`/`COVER_H` ที่ `build/seo.mjs:63` ใช้ที่ `build/ui.mjs:83` และค่าที่ฝังไว้ 8 จุดใน `build/app.src.js`) ⇒ ไฟล์ที่ขนาดไม่ตรงจะพา CLS กลับมาแบบเงียบ ๆ ทั้งที่โค้ดดูเหมือนประกาศขนาดไว้ครบ · เพดาน 300 KB อยู่ในสัญญาด้วยเพราะไฟล์นี้เป็น**ภาพ LCP ของหน้าแรก** ไม่ใช่เพราะงบของ crawler (ตัวสร้างของ AIO-56 มีบันไดคุณภาพที่การันตีเพดานนี้อยู่แล้ว) · *หมายเหตุความซื่อสัตย์: ช่องโหว่เดียวกันมีอยู่กับ `cover` วันนี้ — V6 ตรวจแค่ว่าไฟล์มีอยู่ ไม่ได้ตรวจว่าเป็น 1024×1536 · ผมบันทึกเป็นงานต่อเนื่องของ Dev ไม่ใช่งานของ AIO-55 และไม่ยอมให้มันเป็นข้ออ้างให้ `coverWide` หลวมตาม*

### 13.5 หลักการที่ล็อกลง ADR: **ที่วางประกาศทรงที่ต้องการ ไม่ใช่ประกาศไฟล์ที่จะใช้**

ที่วางบอกว่า "ฉันต้องการทรงไหน" แล้ว **ตัวเลือกไฟล์ที่เดียว** ตัดสินว่าได้ไฟล์ใบไหน · ที่วางห้ามเขียนชื่อฟิลด์ `cover`/`coverWide` เองเลย

ทรงที่ขอได้มีสามค่า และต้องมีแค่สามค่านี้:

| ค่าที่ขอ | ความหมาย | ตัวเลือกไฟล์คืนอะไร |
|---|---|---|
| `poster` (**ค่าตั้งต้น**) | ช่องนี้เป็นกรอบ 2:3 เสมอ ไม่ว่าเรื่องจะเป็นทิศไหน | `cover` เสมอ |
| `wide` | ช่องนี้เป็นกรอบกว้างเสมอ ไม่ว่าเรื่องจะเป็นทิศไหน | `coverWide ?? cover` (ถอยกลับ = ครอปแบบวันนี้) |

### 13.6 ฮีโร่ต้องการสองทรงพร้อมกัน — ทางที่เลือกคือ `<picture>`

**D6** `<picture>` ที่มี `<source media="(min-width:720px)" srcset="<coverWide>">` และ `<img src="<cover>" …>` เป็นลูกตัวสุดท้าย

```html
<picture>
  <source media="(min-width:720px)" srcset="/assets/covers-wide/ceo-cold.webp" width="2640" height="1200">
  <img src="/assets/covers/ceo-cold.webp" width="1024" height="1536" alt="" aria-hidden="true"
       loading="eager" decoding="async" fetchpriority="high">
</picture>
```

**เบรกพอยต์ 720px ไม่ใช่เลขที่เลือกเอง** — มันคือจุดที่กล่องฮีโร่เปลี่ยนจากกรอบ 2:3 เป็นแถบนอน (`@media (min-width:720px)` → `.hero .bg{aspect-ratio:auto;height:min(440px,56vh)}` ที่ `assets/site.css:270-271`) ถ้า Visual ย้ายเบรกพอยต์นั้น ค่าใน `media` ต้องย้ายตาม ⇒ ต้องมีด่านที่จับความไม่ตรงนี้ ไม่ใช่คอมเมนต์เตือน · ด่านที่ถูกคือวัดของจริงด้วยเครื่องมือที่วัดกล่องฮีโร่อยู่แล้ว (`tools/test-layout.mjs` ส่วน `hero`): ที่ความกว้าง 719px ภาพที่เบราว์เซอร์เลือกต้องเป็นไฟล์ 2:3 · ที่ 720px ต้องเป็นไฟล์กว้าง

เหตุผลที่เลือกทางนี้ เทียบกับทางที่ทิ้ง:

| ทาง | ทิ้งเพราะ |
|---|---|
| `background-image` + media query | ทิ้ง `<img>` จริงไป ⇒ ขัด AC-5 ที่ `build/ui.mjs:79-81` ("ปก: `<img>` จริงเสมอ") · เสีย `width`/`height` ที่กัน CLS · เสีย `fetchpriority="high"` บนภาพ LCP ของหน้าแรก |
| `<img>` สองใบ + `display:none` | เบราว์เซอร์บางตัวโหลดทั้งสองใบ ⇒ จ่าย bytes สองเท่าบนภาพ LCP · และมี `<img>` สองตัวที่ alt ต้องตรงกันตลอด |
| ไฟล์กว้างใบเดียวทุกจอ | ฮีโร่มือถือเป็นกรอบ 2:3 ตามแบบที่ลูกค้าอนุมัติ ⇒ เป็นการแก้แบบ ไม่ใช่การแก้บั๊ก |
| `srcset`/`sizes` (ไม่มี `media`) | `srcset` ใช้เลือก**ความละเอียด**ของภาพทรงเดียวกัน ไม่ใช่เลือก**ทรง** · เบราว์เซอร์มีสิทธิ์เลือกใบไหนก็ได้ตาม DPR ⇒ ไม่รับประกันทรง |

**ข้อดีที่ทำให้ทางนี้ปลอดภัยที่สุด:** `<img>` ยังเป็นปก 2:3 ⇒ ถ้าไม่มี `coverWide` ให้ตัดบล็อก `<source>` ออก แล้วผลลัพธ์คือ HTML เดิมเป๊ะ ไม่ใช่ HTML ที่คล้ายเดิม · เบราว์เซอร์เลือกไฟล์ก่อนวางเลย์เอาต์ จึงไม่มีจังหวะที่ภาพผิดทรงโผล่

**เลขที่ต้องพูดตรง ๆ กับลูกค้า:** ไฟล์ 11:5 ในกล่องฮีโร่เดสก์ท็อป (วัดได้ 1248×480 = ar 2.6) **ยังถูกครอปความสูง ~15%** และที่ 1366×768 (กล่อง 1248×430 = ar 2.9) **~24%** — ดีขึ้นจาก ~74% และ ~78% วันนี้ แต่ไม่ใช่ศูนย์ · ทางที่จะทำให้เป็นศูนย์คือไฟล์ใบที่สามต่อเรื่องสำหรับที่วางเดียว ซึ่ง **ผมไม่เอา**: สามใบต่อเรื่องแลกกับช่องเดียว และของที่ Visual ทำแทนนั้นดีกว่า — บังคับให้ของสำคัญทุกชิ้นอยู่ในกรอบกลาง (เว้นขอบด้านละ 12.1%) ⇒ ส่วนที่ถูกครอปเป็นบรรยากาศ ไม่ใช่งานศิลป์ · และสัดส่วนของกล่องฮีโร่เองเป็นของ UX ที่ตัดสินไปแล้วใน AIO-38 (เพดาน 56vh) ถ้า UX เปลี่ยนความสูงกล่องวันหน้า `coverWide` ใบเดิมยังใช้ได้ต่อ

### 13.7 วันที่วิดีโอแนวนอนมาถึง

**D7 · กล่องเพลเยอร์มาจาก `orientation` ไม่ใช่โทเคน**

วันนี้ `.player{aspect-ratio:var(--ar-reel)}` (`assets/site.css:514`) ตายตัว 9:16 · ไฟล์โทเคนเขียนขอบเขตการใช้กำกับไว้ทุกตัว (`assets/tokens.css:121-123`: `--ar-poster` = "ปกทุกที่ในเว็บ" · `--ar-reel` = "เพลเยอร์ + ฟีด เท่านั้น" · `--ar-cont` = "การ์ดดูต่อ เท่านั้น") ⇒ กฎของสัญญา:

1. **ทิศต้องถูกเขียนลงบนกล่องเพลเยอร์โดย build** (คลาสหรือ custom property บนตัว `.player` เอง) ที่จุดเดียวสองที่ คือ `build/pages-watch.mjs:136` และ `build/pages-discovery.mjs:159` แล้ว CSS อ่านจากกล่องนั้น · **ห้าม**ให้ JS ไปวัดภาพแล้วเดาทิศตอนรัน และ**ห้าม**ให้ CSS เดาจากขนาดจอ
2. **ห้ามขยายความหมายของโทเคนที่มีอยู่** — `--ar-reel` คงความหมาย "เพลเยอร์/ฟีดของ**เรื่องแนวตั้ง**" (ขอบเขตนี้ไม่เปลี่ยนแม้ฟีดจะรับทุกเรื่องแล้วตาม D8 ฉบับกลับทาง — เรื่องแนวนอนในฟีดใช้โทเคนใหม่ของข้อนี้ ไม่ใช่ยืมตัวนี้) · `--ar-cont` คงความหมาย "การ์ดดูต่อ" แม้ค่าจะเป็น 16/9 เหมือนกันก็ห้ามยืมใช้ เพราะวันที่ใครปรับค่าใดค่าหนึ่งจะลากอีกช่องไปด้วยเงียบ ๆ · ค่า 16:9 ของเพลเยอร์ต้องเป็น **โทเคนใหม่** · ชื่อและค่าเป็นของ Visual (§13.10)
3. **ไฟล์วิดีโอยังไม่เปิดในรอบนี้** — ช่องวิดีโอยังต้องรอ ADR-002 ตาม §6.7 ไม่เปลี่ยน · §13 ทำให้ "วันที่วิดีโอมาถึง" ไม่ต้องรื้อ ไม่ใช่เปิดทางให้เติมไฟล์วิดีโอโดยถือ ADR-001 เป็นฐาน

**D8 · ฟีดรวมทุกเรื่อง — กลับทางจากฉบับแรกโดยมติลูกค้า 25 ต.ค. 2026 12:14Z**

ฉบับแรกของข้อนี้ (ข้อเสนอของ CEO ที่ผมรับไปเขียน) ตัดว่าฟีดไม่รับเรื่องแนวนอน · เจ้าของงานตัดสินกลับทาง: **ฟีดต้องมีทุกเรื่อง** ⇒ ข้อนี้เขียนใหม่ทั้งข้อ · **ผมไม่ลบเหตุผลเก่า เพราะเหตุผลเก่าคือรายการโจทย์ที่ต้องแก้** — มันไม่ได้ผิด มันแค่เลิกเป็นเหตุผลให้ตัดของออก:

| ข้อเท็จจริงที่ยังจริงทุกตัวอักษร | เคยใช้เป็นเหตุผลให้ "ไม่รวม" | ตอนนี้เป็นอะไร |
|---|---|---|
| `/feed/` เป็นหน้าเลื่อนเต็มจอทีละเรื่อง (`body.stage` · `.player.full{height:calc(100dvh - var(--navh))}`) ⇒ คลิป 16:9 ในกรอบเต็มจอมือถือ 9:16 เหลือภาพจริงราว **32% ของความสูงจอ** ที่เหลือเป็นพื้นว่าง | ตัดออกจากฟีด เพราะแย่กว่าการครอปวันนี้ | **โจทย์ของ UX (AIO-59)** — ต้องมีกฎกรอบที่ไม่ปล่อยให้เหลือแถบว่างครึ่งจอ · **ADR ไม่ตัดสินว่าเติมอะไรในพื้นที่ที่เหลือ** |
| เครื่องเรือนของฟีด — ตัวนับใน `.ptop` · แคปชันและปุ่มแถวขวาใน `.pstack`/`.side` — วางตำแหน่งสัมบูรณ์เทียบกล่องเต็มจอ (บล็อก `.player.full` ใน `buildFeed()` ของ `build/pages-discovery.mjs`) | เปลี่ยนทรงกล่องกลางฟีด = วางผังใหม่ ไม่ใช่เปลี่ยนสัดส่วน ⇒ ไม่คุ้ม | **ยังเป็นงานวางผังจริง และตอนนี้ต้องทำ** — เป็นของ AIO-59 · สัญญาบังคับแค่ว่ากล่องสื่อต้องมีทรงที่ประกาศจากข้อมูลและวัดได้ (V17 ข้อ **ค**) |
| **การเอาตัวกรองออกเฉย ๆ = ฟีดที่มีแถบว่างครึ่งจอ** ซึ่งไม่ใช่ของที่ลูกค้าสั่ง | — | **ข้อห้ามของรอบนี้** · ห้ามส่งขั้นที่ปลดตัวกรองโดยที่กล่องสื่อยังไม่ได้ทรงจาก `orientation` — สองอย่างนี้เข้าด้วยกันหรือไม่เข้าเลย (ลำดับใน §13.8) |

**แหล่งความจริงของการวาง:** ทรงของกล่องสื่อในกรอบเต็มจอ · ที่อยู่ของเครื่องเรือนเมื่อกล่องสื่อไม่เต็มจอ · สิ่งที่เติมพื้นที่ที่เหลือ · จังหวะเปลี่ยนทรงตอนปัดข้ามเรื่อง = **ของ UX-Designer (AIO-59) ทั้งหมด** ⇒ ห้ามอ่าน §13 เป็นคำตอบของข้อพวกนี้ · ที่ §13 บังคับมีสามข้อเท่านั้น: (ก) **ฟีดมีทุกเรื่อง** (ข) **กล่องสื่อของแต่ละเรื่องมีทรงที่ประกาศจาก `orientation` และวัดได้** (ค) **ค่าที่ประกาศมาจากข้อมูล ไม่ใช่จากการเดาตอนรัน** (ต่อจาก D7 ข้อ 1)

**กฎที่ต้องเขียนให้ครบ ไม่ใช่แค่ "ฟีดรวมทุกเรื่อง"** — ตารางนี้กลับทางจากฉบับแรก: เดิมต้องพิสูจน์ว่าไม่มีเรื่องแนวนอน**หลุดเข้า** · ตอนนี้ต้องพิสูจน์ว่า **ไม่มีเรื่องไหนหายไปจากฟีด** และทุกเรื่องได้ทรงของตัวเอง:

| รอย | ของจริงวันนี้ | สัญญา |

| ทิศของกล่องเพลเยอร์ในฟีด | **ไม่มีใครเขียนทิศลงกล่องเลย** — `.player.full` ได้ความสูงเต็มจอตรง ๆ | build เขียนทิศของเรื่องแรกลงบน `#feedPlayer` **และฝั่งเบราว์เซอร์ต้องเขียนทับทุกครั้งที่สลับเรื่อง** ในฟังก์ชัน `show()` ของส่วน 14 — ชื่อเดียว ค่าเดียว สองที่ · นี่คือรอยที่ D8 ฉบับแรกปิดบังไว้: ตอนฟีดมีแต่แนวตั้ง กล่องไม่เคยต้องเปลี่ยนรูป |
| สถานะว่างของฟีด | เคยผูกกับกรณี "ไม่มีเรื่องแนวตั้งเลย" | **กรณีนั้นเกิดไม่ได้แล้วโดยนิยาม** — ฟีด = `series[]` ทั้งชุด ⇒ *ฟีดว่าง ⇔ คลังว่าง* · **ห้ามมีเส้นทางสถานะว่างของฟีดที่ผูกกับทิศ** และห้ามมีข้อความใดบอกผู้ชมว่าฟีดรับเฉพาะละครแนวตั้ง · คลังว่างเป็นกรณีของทั้งเว็บ ไม่ใช่ของผิวนี้ |

**ราคาของการกลับทาง และของที่ต้องถอนออก:** วันนี้ 12/12 เรื่องเป็นแนวตั้งและไม่มีไฟล์วิดีโอในระบบแม้ไฟล์เดียว (`<video` = 0 จุดนอก `design/v2/`) ⇒ **ฟีดยังมีครบ 12 เรื่องเท่าเดิมและหน้าตาไม่ขยับแม้พิกเซลเดียว** การกลับทางจึงไม่มีราคาบนเว็บ · ราคาอยู่ในโค้ดที่เพิ่งลงตาม D8 ฉบับแรก: `FEED_SERIES` ใน `build/content.mjs` (ถัดจาก `isVertical`) เข้ามาในขั้น 1/4 ของ AIO-57 และยังไม่มีใครเรียก ⇒ **ต้องถอนออกพร้อมคอมเมนต์หัวบล็อกของมัน** ไม่ใช่ปล่อยไว้ให้คนหยิบไปใช้ · `isVertical` เก็บไว้ได้ เพราะตัวเลือกไฟล์ `auto` ใน §13.5 ยังต้องถามทิศ · และ **ตัวกรองทิศในเส้นทางฟีดห้ามเข้า main เลย** ไม่ว่าจะเป็นเรื่องแรกที่ฟีดเปิด ชื่อ slug ในแถบรีล หรือสถานะว่าง — ของที่ยังไม่ commit ก็ให้ถอนก่อนส่ง ไม่ใช่ลงไปแล้วตามแก้

### 13.10 สิ่งที่หัวข้อนี้ **ไม่** ตัดสิน

1. **จุดโฟกัสของภาพในกล่องฮีโร่** — `.hero .bg img{object-position:center 22%}` จูนมาสำหรับปก 2:3 ที่ถูกครอปหนัก พอได้ไฟล์ 16:9 ค่านี้ควรกลับเป็นกลาง · **เป็นของ Visual/UX** เพราะ `assets/site.css` สะท้อนกฎใน `design/v2/v2.css` บรรทัดต่อบรรทัด และ `design/v2/` เป็นของ Visual ⇒ เปิดเป็นงานต่อเนื่อง (อ้างกฎด้วย **ชื่อ selector** ไม่ใช่เลขบรรทัด เพราะเลขบรรทัดในไฟล์ของ Visual เลื่อนแล้วทำให้คอมเมนต์เราชี้ผิดมาแล้ว)
2. **ชื่อและค่าของโทเคน 16:9 สำหรับเพลเยอร์** — สัญญาแค่ห้ามยืม `--ar-reel`/`--ar-cont` มาใช้ซ้ำ (§13.7 ข้อ 2) ส่วนชื่อโทเคนเป็นของ Visual
3. **สัดส่วนที่ถูกของกล่องฮีโร่เอง** — ตัดสินแล้วใน AIO-38 (เพดาน 56vh) ไม่เปิดใหม่ในงานนี้
4. **ใครเรนเดอร์ภาพกว้าง 12 ใบ** — งานของ Visual · สายพานมีอยู่แล้วในรูปแบบของ `design/v2/share-cards.mjs` (ภาพแชร์ 13 ใบมาทางนั้น) · Dev ไม่ต้องรอไฟล์เพื่อเริ่ม (§13.3)
5. **ไฟล์วิดีโอจริง** — ยังเป็นของ ADR-002 ตาม §6.7 ไม่เปลี่ยน
6. **ทรงและขนาดของภาพกว้าง (11:5 · 2640×1200)** — เป็นของ Visual · ตัวเลขในสัญญารับมาจาก AIO-56 เพราะมีการวัดรองรับ (§13.4) · ถ้า Visual เปลี่ยน ให้ **แก้ตัวเลขในหัวข้อนี้และใน V15** ไม่ใช่เลิกกฎ "ขนาดเป๊ะ" เพราะเหตุผลของกฎคือแอตทริบิวต์ `width`/`height` มาจากค่าคงที่ · และข้อแม้เดียวของผมคือทรงใหม่ต้องยังทำให้ **ไฟล์ใบเดียวรับได้ทั้งฮีโร่และกรอบ 16/9 ของ `.cont .thumb`** พร้อมกรอบปลอดภัยที่ยังครอบของสำคัญไว้ครบ
7. **กฎกรอบฟีดเมื่อเรื่องเป็นแนวนอน (เพิ่มโดย AIO-58)** — ทรงของกล่องสื่อในกรอบเต็มจอ · ที่อยู่ของ `.ptop`/`.pstack`/`.side` เมื่อกล่องสื่อไม่เต็มจอ · สิ่งที่เติมพื้นที่ที่เหลือ · จังหวะเปลี่ยนทรงตอนปัดข้ามเรื่อง ⇒ **เป็นของ UX-Designer (AIO-59)** · §13 บังคับเฉพาะว่าทรงต้องประกาศจาก `orientation` และวัดได้ (V17 ข้อ ค) · เลข 16/9 ใน V17 คือทรงของ**ไฟล์วิดีโอ** ไม่ใช่คำตัดสินการวาง ⇒ ถ้า AIO-59 กำหนดกรอบที่ไม่ใช่ 16/9 ให้ **แก้ตัวเลขใน V17 ตามกฎนั้น** ไม่ใช่เลิกข้อ ค · และ **ห้ามแก้กลับไปเป็น "ฟีดไม่รับแนวนอน"** ไม่ว่าการวางจะยากแค่ไหน — ข้อนั้นเป็นมติลูกค้า ไม่ใช่คำตัดสินทางเทคนิคของเอกสารนี้
8. **ไฟล์ `default` ใบที่ 13 ของ AIO-56** — สัญญานี้อ้างถึงเฉพาะไฟล์ต่อเรื่องผ่านฟิลด์ `coverWide` · ไฟล์ที่ไม่มีเรื่องอ้างถึงไม่ถือเป็นความผิด (โฟลเดอร์ไม่ใช่แหล่งความจริง ตาม D5) แต่ `build/` จะไม่ใช้มัน จนกว่าจะมีที่วางที่ขอทรงกว้างแบบไม่ผูกกับเรื่อง
