## 1. สภาพจริงที่ตรวจแล้ว (Context)

ตัวเลขทุกตัวในส่วนนี้ผมเปิดไฟล์ตรวจเองวันที่ 23 ต.ค. 2026 ไม่ได้อ้างจากสรุปของใคร ทุกข้ออ้างอิงไฟล์และบรรทัดให้ตรวจซ้ำได้

| สิ่งที่ตรวจ | ผลที่พบ | หลักฐาน |
|---|---|---|
| build step | ไม่มี `package.json` ทั้งรีโป ไม่มี build ไม่มี backend | `git ls-files` 240 ไฟล์ ไม่มี `package.json` |
| ไฟล์วิดีโอ | แท็ก `<video` ทั้งรีโป = **0** | `grep -r "<video" . --exclude-dir=.git \| wc -l` → `0` |

### 1.1 สามเรื่องที่ผมเจอเพิ่ม และมันเปลี่ยนรูปของงาน

**(ก) ธงล็อกตอนมีความหมายกลับด้านจากที่อ่านเผิน ๆ และของจริงล็อกไว้ 298 ตอน**

`episodes` เก็บเป็น tuple 3 ช่อง `[ชื่อ, "m:ss", ธง]` ทั้ง 418 ตอน ธงช่องที่สามไม่ใช่ "ล็อก" แต่คือ "ดูได้" — ค่า `false` คือตัวที่ถูกล็อก ดูที่ `assets/app.js:118` ใส่คลาส `lock` เมื่อ `x[2]` เป็นเท็จ และ `assets/app.js:123` เด้ง toast `'ตอนนี้สำหรับสมาชิก'` เมื่อ `!s.episodes[ep-1][2]`

นับจริง: `true` (ดูได้) = **120 ตอน** · `false` (ล็อก) = **298 ตอน** จาก 418

แปลว่าวันนี้เว็บยังล็อก 298 จาก 418 ตอน ขัดมติ "ดูฟรีทุกตอน" อยู่ในโค้ดที่ยังรันได้ ใครจะทำ migration ต้องรู้ว่าทิศของธงคือทิศนี้ ไม่ใช่ทิศตรงข้าม เพราะถ้าอ่านกลับด้านจะเผลอล็อก 120 ตอนและปล่อย 298 ตอน

**(ข) เรื่องย่อซ้ำประโยคโปรย — พบตำแหน่งที่ทำให้มันซ้ำแล้ว**

ในม็อกอัพที่อนุมัติ หน้ารายละเอียดเรื่องพิมพ์ `s.hook` สองครั้งติดกัน: `design/v2/pages-discovery.mjs:535` พิมพ์เป็นบรรทัดนำ แล้ว `design/v2/pages-discovery.mjs:537` พิมพ์ซ้ำอีกครั้งเป็นต้นประโยคของย่อหน้าเรื่องย่อ ไม่ใช่ความพลาดของ Visual — `assets/data.js` ไม่มีฟิลด์เรื่องย่อให้ใช้ จึงต้องหยิบ `hook` มาใช้สองหน้าที่ นี่คือเหตุผลที่ §6 แยก `synopsis` ออกจาก `hook` เป็นสองฟิลด์ และมีกฎตรวจห้าม `synopsis` ขึ้นต้นด้วยหรือมี `hook` ซ้ำคำต่อคำ (§6.4 กฎ V7)

**(ค) generator ของ v2 สั่งงานฝั่ง Dev ไว้แล้ว แต่สั่งเกินมติไปสองฟิลด์**

`design/v2/lib.mjs:19` เขียนว่า *"UX 8.2 ระบุให้ Dev เพิ่ม views / tropes[] / releaseDay / freeEps / coinPerEp"* — สี่ตัวแรกรับได้ แต่ **`freeEps` และ `coinPerEp` ต้องไม่เข้าสัญญาข้อมูลนี้** เพราะเป็นของยุคเหรียญที่มติ 22 ต.ค. 2026 ตัดไปแล้ว ตัว Visual เองก็ถอดค่าคงที่พวกนั้นออกจาก rev.2 แล้วตามคอมเมนต์ `design/v2/lib.mjs:38-39` เหลือแต่บรรทัด 19 ที่เป็นข้อความค้าง ผมตัดสินใจไม่รับสองฟิลด์นี้ และใส่กฎตรวจอัตโนมัติไว้กันคนเติมกลับ (§6.4 กฎ V8)

ส่วนที่ generator ชดเชยไว้เองชั่วคราว ทั้งหมดต้องย้ายมาเป็นข้อมูลจริงใน `content.json`:

| สิ่งที่ generator ทำชั่วคราว | ตำแหน่ง | ย้ายไปเป็น |
|---|---|---|
| `views` เป็นสตริงฝังตาย 12 ค่า (`'12.4M'`) | `design/v2/lib.mjs:22-27` | `views` เป็นจำนวนเต็มหรือ `null` (§6.3) |
| `tropes` แมปจาก `hook` ด้วยมือ 3 กลุ่ม รอฝ่ายคอนเทนต์ยืนยัน | `design/v2/lib.mjs:29-36` | `tropes[]` + ทะเบียนแท็ก รอ AIO-20 (§6.5) |
| `releaseDay` ถอดจากข้อความ `status` ด้วยตาราง `DAY` | `design/v2/lib.mjs:41-42` | `status` + `releaseDay` แยกฟิลด์ (§6.2) |
| `cover` คำนวณจาก slug | `design/v2/lib.mjs:44` | `cover` เก็บเป็น path ตรง (§6.3) |

## 2. ข้อจำกัดที่ล็อกแล้ว และเอกสารนี้เคารพอย่างไร

ห้าข้อนี้เป็นมติที่ปิดแล้ว ไม่ใช่ตัวเลือก ผมไม่เสนอทางที่ขัดข้อใดข้อหนึ่ง

| # | ข้อจำกัด | เอกสารนี้เคารพที่ไหน |
|---|---|---|
| 1 | ดูฟรีทุกตอน ไม่มีเหรียญ ไม่มี paywall ไม่มีค่าสมาชิก | §6 ไม่มีฟิลด์ราคา/เหรียญ/ตอนฟรี · กฎ V8 ทำให้ build ล้มถ้ามีคนเติมเข้ามา |
| 2 | ไม่มีบัญชีผู้ชม · ของส่วนตัวอยู่ใน `localStorage` เท่านั้น | §5 แยก admin auth ออกจาก viewer login ชัดเจน · §6.6 ห้าม `following`/`cont` เข้า `content.json` |
| 3 | หน้าที่ให้ Google เก็บ ต้องมีเนื้อหาจริงใน HTML ตั้งแต่ตอนส่ง | §4 ทางเลือกทุกทางเป็น static pre-render · §4.5 เกณฑ์ตรวจว่าไม่ซ้ำรอย `watch/ceo-cold.html:36` |
| 4 | ห้าม deploy ห้ามตั้งโดเมน ห้ามซื้อบริการ | §8 — เอกสารนี้จบที่ build artifact ไม่มีคำสั่งปฏิบัติการใด ๆ ตัวเลขใน §4.4 เป็นราคาตั้งเพื่อประกอบการตัดสินใจของลูกค้า ไม่ใช่ใบสั่งซื้อ |
| 5 | ยอดวิว/คะแนนที่ไม่มีระบบวัดรองรับ ห้ามเข้า structured data | §7 — เงื่อนไขปลดล็อกเขียนเป็นเช็กลิสต์ที่เครื่องตรวจได้ |

## 3. "หลังบ้าน" คืออะไร — รับการตีความ และมีข้อค้านหนึ่งข้อที่อยากให้ถามลูกค้า

### 3.1 รับการตีความว่า = แผงจัดการเนื้อหา (admin/CMS)

**เห็นด้วย** และข้อมูลหนุนชัดกว่าที่คิด ไม่ใช่แค่ "ชื่อตอนซ้ำ" แต่เป็น:

- ชื่อตอนไม่ซ้ำ 32 ชื่อ ต่อ 418 ตอน — ซ้ำเฉลี่ย 13 ครั้ง คนอ่านเจอแน่
- ข้อมูลเดียวกันถูก pre-render ไว้ในหน้า static พร้อม ๆ กับที่ `assets/data.js` ถืออีกชุด แก้ชื่อเรื่องเดียวต้องไล่แก้หลายไฟล์ และไม่มีอะไรรับประกันว่าสองที่ตรงกัน
- บริษัทไม่มีฝ่ายคอนเทนต์ คนที่จะแก้คือคนที่ไม่ได้เขียนโค้ด การให้แก้ `assets/data.js` บรรทัดเดียว 36 KB เป็นทางที่พังแน่

CMS แก้ทั้งสามข้อ และ §6 (สัญญาข้อมูล) คือสิ่งที่แก้ข้อที่สองได้จริง เพราะบังคับให้มีแหล่งความจริงแหล่งเดียว

### 3.2 ข้อค้าน — ขอให้ถามลูกค้าหนึ่งคำถาม ก่อนปิดคำว่า "หลังบ้าน" ที่ CMS

ผมไม่ค้านว่า CMS ผิด ผมค้านว่า **CMS ไม่น่าจะเป็น "หลังบ้าน" ทั้งก้อนที่ลูกค้าคิดไว้** และถ้าเราปิดคำนี้ที่ CMS เงียบ ๆ เราจะส่งของที่ยังดูละครไม่ได้

เหตุผลเป็นรูปธรรม: **เว็บดูละครนี้มีแท็ก `<video` ทั้งรีโป = 0** หน้ารับชมทั้ง 12 หน้าเป็นปกนิ่งกับซับทับภาพ และ `assets/app.js:125` ใช้ `setInterval` เดินแถบเวลาเลียนแบบการเล่น ไม่มีไฟล์มีเดียแม้ไฟล์เดียว ไม่มีที่เก็บ ไม่มี CDN ไม่มี transcode ไม่มีพิกัดค่าแบนด์วิดท์

ถ้าลูกค้าพูดคำว่า "หลังบ้าน" โดยนึกถึง "ที่ที่เอาคลิปขึ้นแล้วคนดูได้" CMS ที่พิมพ์ชื่อตอนสวยจะไม่ตอบโจทย์นั้นเลยแม้แต่ส่วนเดียว และช่องว่างนี้ใหญ่กว่าเรื่องชื่อตอนซ้ำมาก

สิ่งที่ผมขอ ไม่ใช่ให้เปลี่ยนงานนี้ แต่ขอให้ถามลูกค้าหนึ่งคำถามว่า **"ตอนนี้คลิปละครอยู่ที่ไหน และใครจะเอาขึ้น"** แล้วได้คำตอบมาสามทาง:

- ถ้าลูกค้าตอบว่า "ยังไม่มีคลิป ขอจัดระเบียบข้อมูลก่อน" → ADR-001 นี้ครบ เดินต่อได้ทันที ไม่ต้องแก้อะไร
- ถ้าตอบว่า "มีคลิปอยู่แล้ว/จะมี" → ต้องมี **ADR-002 ว่าด้วยมีเดียและการส่งวิดีโอ** แยกฉบับ เพราะมันมีค่าแบนด์วิดท์ต่อเดือนที่ขึ้นกับจำนวนคนดู คนละแบบกับ §4.4 ที่เป็นค่าคงที่ และเรื่องเงินเป็นของลูกค้า
- ถ้าตอบว่า "ฝากไว้ YouTube/ผู้ให้บริการอื่น" → ยังต้องมี ADR-002 แต่เล็กกว่ามาก และ `content.json` จะต้องเพิ่มฟิลด์อ้างอิงวิดีโอ ซึ่ง §6.7 เตรียมที่ว่างไว้แล้วแบบไม่ต้องแก้สัญญาย้อนหลัง

**เอกสารนี้จึงประกาศขอบเขตตัวเองว่า: ADR-001 ครอบคลุมแผงจัดการเนื้อหาและเส้นทางเผยแพร่ข้อความ/ข้อมูล ไม่ครอบคลุมการเก็บและส่งไฟล์วิดีโอ** ใครอ่านเอกสารนี้แล้วคิดว่างานหลังบ้านจบ จะเข้าใจผิด

### 3.3 คำตอบที่ได้ — ปิดข้อค้าน §3.2 แล้ว

คำถามใน §3.2 ถูกถามผ่านการ์ดคำถามบน AIO-21 และ **ลูกค้าตอบแล้วเมื่อ 22 ต.ค. 2026 21:34 UTC (23 ต.ค. เวลาไทย)** ว่า:

> **"ยังไม่มีคลิป ขอจัดระเบียบข้อมูลก่อน"**

ผลตามที่ §3.2 ผูกไว้ล่วงหน้า ไม่ใช่การตีความใหม่หลังรู้คำตอบ:

| | ผล |
|---|---|
| ADR-001 | **ครบตามขอบเขต** ไม่ต้องแก้สาระใด — เอกสารนี้จึงเป็น Accepted |
| ADR-002 (มีเดีย/วิดีโอ) | **ยังไม่ต้องเขียน** · ไม่ใช่ว่าไม่ต้องมีตลอดไป — จะต้องมีในวันที่ลูกค้ามีคลิปจริง และเงื่อนไขนั้นยังอยู่ |
| §6.7 ฟิลด์อ้างอิงวิดีโอใน `episodes[]` | **ยังปิดอยู่** ห้ามเติมโดยถือ ADR-001 เป็นฐาน · เงื่อนไขเดิมคงไว้ทุกตัวอักษร: ต้องมี ADR-002 อนุมัติก่อน |
| §4.5 (ทบทวนทางเลือก C) | ไม่ต้องทบทวน เพราะไม่มีภาระวิดีโอเข้ามา |

**ข้อที่ยังจริงอยู่หลังได้คำตอบ และต้องไม่ถูกลืม:** คำตอบนี้ปิดคำถามว่า "ตอนนี้ต้องทำวิดีโอไหม" (ไม่ต้อง) แต่ไม่ได้เปลี่ยนสภาพของเว็บ — หน้ารับชมยังเป็นปกนิ่งกับซับทับภาพ และ `assets/app.js:125` ยังใช้ `setInterval` เดินแถบเวลาเลียนแบบการเล่นอยู่ ดังนั้นประโยคใน §3.2 ที่ว่า **"ใครอ่านเอกสารนี้แล้วคิดว่างานหลังบ้านจบ จะเข้าใจผิด" ยังมีผล** — "หลังบ้านเสร็จ" ในความหมายของ ADR นี้ = แผงจัดการเนื้อหาและเส้นทางเผยแพร่ข้อมูลเสร็จ ไม่ใช่ "เอาคลิปขึ้นแล้วคนดูได้"

## 4. Stack และที่เก็บข้อมูล — ทางเลือกและเหตุผลที่เลือก

### 4.0 เกณฑ์ตัดสิน

เว็บนี้ไม่มีรายได้จากผู้ชมเลย (มติข้อ 1) เกณฑ์เรียงตามน้ำหนัก:

1. ฝั่งผู้ชมต้องไม่ต้องมีเซิร์ฟเวอร์เปิด 24 ชม. — คนดูโหลด HTML นิ่งจาก CDN เท่านั้น
2. ค่าใช้จ่ายคงที่ต่อเดือนต้องต่ำและคาดเดาได้ ไม่ผูกกับจำนวนคนดู
3. HTML ต้องมีเนื้อหาจริงตอนส่ง (มติข้อ 3)
4. จำนวนชิ้นส่วนที่ต้องดูแลต้องน้อย เพราะทีมเล็กและไม่มีฝ่ายคอนเทนต์
5. ข้อมูลต้องมีประวัติการแก้ ย้อนได้ว่าใครแก้อะไรเมื่อไร

ข้อ 1 ตัด "เว็บแอปที่ render ตอน request" ออกทั้งตระกูลตั้งแต่ต้น ทั้งสามทางข้างล่างจึงเป็น static ฝั่งผู้ชมเหมือนกันหมด ต่างกันแค่ที่ "แผงแก้ข้อมูลอยู่ที่ไหน และข้อมูลนอนอยู่ที่ไหน"

### 4.1 ทางเลือก A — Git เป็นที่เก็บข้อมูล (Git-as-CMS) · **ทางที่เลือก**

`content.json` เป็นไฟล์ในรีโป เป็นแหล่งความจริงแหล่งเดียว แผงจัดการเป็นหน้า static ที่รันในเบราว์เซอร์ของทีมงาน อ่าน `content.json` มาแก้ในฟอร์ม แล้วเขียนกลับเป็น commit ผ่าน Git API ของผู้ให้บริการรีโป การ commit จุด CI ให้ validate แล้ว build HTML ใหม่

- **ฝั่งผู้ชม** — ไฟล์ static บน CDN ไม่มีเซิร์ฟเวอร์
- **ฝั่งแอดมิน** — static page + Git API ไม่มีเซิร์ฟเวอร์เปิดค้าง
- **ที่เก็บข้อมูล** — ไฟล์ JSON ใน git ประวัติการแก้ได้ฟรีจาก git log
- **ข้อดี** — ชิ้นส่วนน้อยที่สุด (ไม่มี DB ไม่มีเซิร์ฟเวอร์) · ประวัติ/ย้อนกลับได้ในตัวด้วย `git revert` · ตรวจรีวิวข้อมูลเหมือนรีวิวโค้ดได้ · ข้อมูล 36 KB อยู่ในขนาดที่ไฟล์เดียวสบาย ๆ
- **ข้อเสีย** — แก้พร้อมกันหลายคนจะชน (รับได้: ทีมไม่มีฝ่ายคอนเทนต์ คนแก้คือหน่วยเดียว) · แก้แล้วเห็นผลช้าเท่าเวลา build ไม่ใช่ทันที · ขนาดไฟล์จะเริ่มอึดถ้าเกินหลักหลาย MB (ไกลมาก จาก 36 KB)

### 4.2 ทางเลือก B — Headless CMS สำเร็จรูป

ใช้บริการ CMS สำเร็จรูปเก็บเนื้อหา ทีมงานแก้ในแผงของผู้ให้บริการ แล้ว webhook จุด CI ให้ดึงข้อมูลออกมาเป็น `content.json` แล้ว build static เหมือนเดิม

- **ข้อดี** — แผงแก้ข้อมูลดีกว่าที่เราเขียนเองแน่นอน · มี role/ประวัติ/preview ให้ฟรี · แก้พร้อมกันหลายคนได้
- **ข้อเสีย** — ข้อมูลจริงไปนอนที่ผู้ให้บริการ เราถือแค่สำเนา ผูกกับเจ้าของบริการ · ต้องมีงาน export ไม่งั้นย้ายออกยาก · มีเพดาน free tier ที่โตแล้วต้องจ่าย · เพิ่มบริการภายนอกหนึ่งเจ้าที่ต้องดูแลบัญชีและกุญแจ

### 4.3 ทางเลือก C — แอดมินของเราเองบนเซิร์ฟเวอร์ + ฐานข้อมูล

Node + ฐานข้อมูลสัมพันธ์บน VPS เล็ก เปิดเฉพาะแผงแอดมิน กด publish แล้วไป build static

- **ข้อดี** — ยืดหยุ่นที่สุด ทำ workflow อะไรก็ได้ · เป็น stack ที่โตไปทำ ADR-002 ต่อได้ตรง ๆ
- **ข้อเสีย** — มีเซิร์ฟเวอร์เปิดค้างให้ดูแล แม้จะเป็นฝั่งแอดมิน · ต้อง backup DB เอง (git ให้ฟรีในทาง A) · ของที่ต้องดูแลเยอะที่สุดและแพงที่สุด เพื่อแลกความยืดหยุ่นที่งานตอนนี้ยังไม่ต้องใช้

### 4.4 ค่าใช้จ่ายต่อเดือน เป็นตัวเลข

ราคาตั้งที่ประกาศสาธารณะ ณ ต.ค. 2026 · แปลงที่ 1 USD ≈ 36 THB · **ตัวเลขนี้ไว้ให้ลูกค้าตัดสินใจ ไม่ใช่ใบสั่งซื้อ และเอกสารนี้ไม่ได้ขอให้ซื้ออะไรทั้งนั้น** (§8)

| | A · Git-as-CMS | B · Headless CMS | C · เซิร์ฟเวอร์ + DB |
|---|---|---|---|
| โฮสต์ไฟล์ static (ฝั่งผู้ชม) | 0 THB — free tier ของ static host | 0 THB | 0 THB |
| ที่เก็บข้อมูล | 0 THB — git repo ที่มีอยู่แล้ว | 0 THB ใน free tier · เกินเพดานเริ่ม ~1,050 THB | ~210 THB (รวมใน VPS) |
| เซิร์ฟเวอร์แอดมิน | 0 THB — ไม่มี | 0 THB — ของผู้ให้บริการ | ~210–430 THB (VPS 1–2 vCPU) |
| CI สำหรับ build | 0 THB — free tier (build ~1–2 นาที ไม่กี่ครั้งต่อวัน) | 0 THB | 0 THB |
| backup | 0 THB — git เป็น backup | 0 THB แต่ต้องเขียน export เอง | ~70–140 THB |
| **รวมกรณีใช้ free tier** | **0 THB/เดือน** | **0 THB/เดือน** | **~280–570 THB/เดือน** |
| **รวมกรณีจ่ายเต็มเมื่อโต** | **~150 THB/เดือน** | **~1,050–1,800 THB/เดือน** | **~570–1,100 THB/เดือน** |

สมมติฐานที่ตัวเลขยืนอยู่บน: 12 เรื่อง 418 ตอน ข้อมูล 36 KB · ปริมาณคนดูยังอยู่ในชั้นฟรีของ static host · **ไม่รวมค่าโดเมนและไม่รวมค่าแบนด์วิดท์วิดีโอ** เพราะยังไม่มีโดเมนในรีโป (ไม่มี `CNAME`) และยังไม่มีไฟล์วิดีโอ (`<video` = 0) ค่าวิดีโอเป็นเรื่องของ ADR-002 ตาม §3.2 และมันไม่คงที่ต่อเดือนแบบตารางนี้

### 4.5 ตัดสินใจ: เลือก A

เลือก **ทางเลือก A — Git-as-CMS** ด้วยเหตุผลเรียงตามน้ำหนัก:

1. **ถูกที่สุดและคาดเดาได้** 0 THB/เดือน และเพดานตอนโตยังอยู่หลักร้อย ไม่ใช่หลักพัน — สำคัญมากเพราะเว็บนี้ไม่มีรายได้จากผู้ชมเลย ทาง B ดูฟรีเท่ากันตอนเริ่ม แต่เพดานของมันสูงกว่า A ราวสิบเท่า
2. **ชิ้นส่วนน้อยที่สุด** ไม่มีเซิร์ฟเวอร์ ไม่มี DB ไม่มีบัญชีผู้ให้บริการเพิ่ม — ตรงกับทีมที่ไม่มีฝ่ายคอนเทนต์และไม่มีคนเฝ้าเซิร์ฟเวอร์
3. **ข้อมูลอยู่กับเรา** แหล่งความจริงคือไฟล์ในรีโปเรา ไม่ใช่สำเนาของข้อมูลที่นอนอยู่ที่คนอื่น ไม่มีงาน export ให้ต้องทำ ไม่มี vendor lock-in
4. **ประวัติและย้อนกลับได้ฟรี** แก้ข้อมูลผิดแล้ว `git revert` ได้ทันที และตอบได้ว่าใครแก้อะไรเมื่อไรจาก git log — ทาง C ต้องสร้างกลไกนี้เองทั้งหมด
5. **ข้อเสียของ A ไม่กัดงานนี้** ข้อเสียหลักคือการแก้พร้อมกันหลายคนจะชน ซึ่งเป็นปัญหาของทีมที่มีฝ่ายคอนเทนต์หลายคน — เราไม่มี ถ้าวันหนึ่งมี ให้ย้ายไป B โดย `content.json` ไม่ต้องเปลี่ยนรูป (ดู §4.6)

เหตุผลที่ **ไม่เลือก B**: จุดแข็งของมันคือแผงที่ดีและการทำงานหลายคน ซึ่งเป็นของที่เรายังไม่ต้องใช้ แต่ราคาที่จ่ายคือข้อมูลจริงย้ายออกไปอยู่นอกมือเรา และผูกกับผู้ให้บริการหนึ่งเจ้า — แพงเกินของที่ได้ ณ ขนาดนี้

เหตุผลที่ **ไม่เลือก C**: แพงที่สุด ของที่ต้องดูแลมากที่สุด และความยืดหยุ่นที่มันให้มาคือความยืดหยุ่นที่งานตอนนี้ยังไม่ต้องใช้ ถ้าคำตอบของลูกค้าใน §3.2 ออกมาว่าต้องทำ ADR-002 เรื่องวิดีโอจริง ทาง C อาจกลับมาน่าสนใจ — **ให้ทบทวนข้อนี้ใหม่ตอนทำ ADR-002 ไม่ใช่ตอนนี้**

### 4.6 สิ่งที่ทำให้การตัดสินใจนี้ย้อนกลับได้

จุดสำคัญที่ทำให้เลือก A ได้อย่างไม่เสี่ยง: **ทั้งสามทางมี `content.json` รูปเดียวกันตาม §6 เป็นจุดส่งของให้ build เหมือนกันหมด** ทาง A เขียนไฟล์ตรง ทาง B ให้ CI ดึงมาแปลงเป็นไฟล์รูปนี้ ทาง C ให้เซิร์ฟเวอร์ export มาเป็นไฟล์รูปนี้ แปลว่าถ้าเปลี่ยนใจ **หน้าบ้านไม่ต้องแก้แม้บรรทัดเดียว** เปลี่ยนแค่ของที่อยู่เหนือไฟล์ขึ้นไป นี่คือเหตุผลที่ §6 คือหัวใจของเอกสารนี้ ไม่ใช่ §4

## 5. Admin auth — ต้องมี และไม่ขัดมติตัดล็อกอินผู้ชม

### 5.1 ทำไมสองเรื่องนี้ไม่ใช่เรื่องเดียวกัน

มติข้อ 2 ตัด **บัญชีผู้ชม** ไม่ได้ตัดการยืนยันตัวตนทุกชนิดในระบบ สองอย่างนี้ต่างกันทุกมิติ:

| | viewer login (ตัดถาวร) | admin auth (ต้องมี) |
|---|---|---|
| ใครใช้ | ผู้ชมทั่วไป ไม่จำกัดจำนวน | ทีมงานบริษัท หน่วยเดียว |
| ป้องกันอะไร | — (ไม่มีอะไรต้องป้องกัน เนื้อหาฟรีทั้งหมด) | สิทธิ์ **เขียน** `content.json` |
| กันการอ่านไหม | — | **ไม่กัน** `content.json` และ HTML ทุกไฟล์เป็นของสาธารณะ ใครก็อ่านได้ |
| เก็บข้อมูลส่วนบุคคลของผู้ชมไหม | เคยจะเก็บ จึงถูกตัด | **ไม่เก็บ** เก็บแค่ตัวตนพนักงานผู้แก้ไข |
| อยู่หน้าไหน | ไม่มีอยู่แล้ว | หน้าแอดมินซึ่งไม่อยู่ในเว็บผู้ชม ไม่มีลิงก์จากหน้าผู้ชม ไม่ถูก index |

สรุปเป็นประโยคเดียวที่เอาไปตอบลูกค้าได้: **ผู้ชมไม่ต้องล็อกอินและจะไม่มีวันต้อง เพราะทุกตอนดูฟรีและไม่มีอะไรผูกกับตัวบุคคล · แต่ "คนที่แก้ข้อมูลเว็บได้" ต้องรู้ว่าเป็นใคร ไม่ใช่เพื่อหวงเนื้อหา แต่เพื่อไม่ให้คนนอกมาแก้ชื่อเรื่องหรือลบตอนได้**

ถ้าไม่มี admin auth เลย ใครก็เขียนทับข้อมูลทั้งเว็บได้ — นั่นเป็นปัญหาคนละเรื่องกับมติเรื่องดูฟรีโดยสิ้นเชิง และมติเรื่องดูฟรีไม่ได้พูดถึงมันเลย

### 5.2 กลไกที่เลือก

ยึดตัวตนจากผู้ให้บริการรีโปที่เราใช้อยู่แล้ว (OAuth) และให้สิทธิ์แก้ข้อมูลตามสิทธิ์เขียนรีโปที่คนนั้นมีอยู่จริง

- ไม่มีตารางผู้ใช้ของเราเอง ไม่มีรหัสผ่านที่เราต้องเก็บหรือรีเซ็ต — ลดของที่จะรั่วให้เหลือน้อยที่สุด
- สิทธิ์ผูกกับสิทธิ์รีโปที่มีอยู่แล้ว คนออกจากทีมแล้วถอนสิทธิ์ที่เดียวจบ
- ร่องรอยการแก้ได้ฟรีจาก commit author — ตอบได้ว่าใครแก้อะไรเมื่อไร โดยไม่ต้องเขียน audit log
- **ห้ามใช้รหัสผ่านร่วมกันทั้งทีม** และ **ห้ามฝัง token ของผู้ให้บริการรีโปไว้ในหน้า static ที่ส่งถึงเบราว์เซอร์** สองข้อนี้เป็นข้อห้ามเด็ด ไม่ใช่คำแนะนำ

### 5.3 ประตูที่ต้องผ่านก่อนโค้ดส่วนนี้เข้า main

ผมเป็นคนกำหนดเกณฑ์นี้และกำหนดว่า: **งานตามแผง admin และเส้นทางเขียนข้อมูลตาม §5.2 ต้องผ่านการเซ็นรับของ Security Engineer ก่อน merge** เพราะมันแตะ OAuth token และเปิดเส้นทางเขียนเข้ารีโป อยู่เหนือเกณฑ์ที่ผมตั้งไว้ชัดเจน · และต้องผ่านรีวิวสองฝั่งครบ (Reviewer-Claude + Reviewer-Codex) ไม่เข้าเกณฑ์งานเล็กที่รีวิวฝั่งเดียวได้

ตัวเอกสาร ADR ฉบับนี้เป็นเอกสาร ไม่ใช่โค้ด จึงไม่ต้องผ่านประตูนั้น แต่โค้ดที่เกิดตามมาต้องผ่าน

## 6. สัญญาข้อมูล `content.json` — ส่วนที่สำคัญที่สุดของเอกสารนี้

นี่คือสิ่งเดียวที่ทำให้ Dev-Claude (หน้าบ้าน) กับ Dev-Codex (หลังบ้าน) ทำขนานกันได้โดยไม่ชนกัน

**กฎการใช้สัญญานี้:**

- หลังบ้าน **ผลิต** ไฟล์รูปนี้ · หน้าบ้าน **บริโภค** ไฟล์รูปนี้ · ไม่มีใครเดารูปจากอีกฝั่ง
- ใครอยากเปลี่ยนรูป ต้องแก้ ADR นี้ก่อน ไม่ใช่แก้โค้ดตัวเองแล้วบอกอีกฝั่งทีหลัง
- `assets/data.js` (`window.LAKORN`) ยังอยู่เพื่อให้เว็บเดิมและ `design/v2/` รันได้ **แต่หมดสถานะแหล่งความจริงทันทีที่ `content.json` มีของจริง** — `design/v2/` อ่าน tuple แบบเดิมและ **ห้ามแก้** (Visual เป็นเจ้าของ) ให้ `design/v2/` คงที่ไว้ ไม่ต้องตามสัญญานี้
- ที่ตั้งไฟล์: `content.json` ที่ราก · เป็น UTF-8 · ไม่ต้องสนใจลำดับคีย์

### 6.1 โครงบนสุด

```json
{
  "version": 1,
  "generatedAt": "2026-10-23T09:00:00+07:00",
  "meta": { "viewsSource": "none" },
  "genres": [ { "slug": "revenge", "label": "แก้แค้น" } ],
  "tropes": [ { "slug": "revenge-karma", "label": "แก้แค้นสาสม" } ],
  "series": [ /* ดู §6.2 */ ]
}
```

| ฟิลด์ | ชนิด | กฎ |
|---|---|---|
| `version` | integer | ขึ้นต้นที่ `1` · ขยับเมื่อเปลี่ยนรูปแบบที่ทำให้ของเก่าอ่านไม่ได้ · หน้าบ้านต้องเช็กและล้มเสียงดังถ้าเจอเลขที่ไม่รู้จัก ไม่ใช่เดาต่อ |
| `generatedAt` | string ISO-8601 มี timezone | เวลาที่สร้างไฟล์ ไว้ดีบั๊กว่าของที่เห็นเก่าหรือใหม่ |

#### 6.3.1 ทำไมแยก `status` ออกเป็นสองฟิลด์

วันนี้ `status` เก็บข้อความไทย 5 แบบ และมันปนสองเรื่องไว้ในฟิลด์เดียว: เรื่องจบหรือยัง กับ ตอนใหม่มาวันไหน พอปนกัน `design/v2/lib.mjs:41-42` จึงต้องมีตาราง `DAY` มาถอดวันออกจากข้อความ ซึ่งแปลว่าถ้ามีคนพิมพ์ข้อความใหม่ที่ไม่อยู่ในตาราง `releaseDay` จะกลายเป็น `null` เงียบ ๆ โดยไม่มีใครรู้

แยกเป็นสองฟิลด์แล้วข้อความไทยที่แสดงกลายเป็นของหน้าบ้านที่ประกอบขึ้นเอง ไม่ใช่ข้อมูลที่ต้องถอดกลับ ตารางย้ายของทั้ง 5 ค่าที่มีอยู่จริง ให้ Dev-Codex ใช้ตอน migrate:

| `status` เดิมใน `assets/data.js` | → `status` | → `releaseDay` |
|---|---|---|
| `"ตอนใหม่ทุกวัน"` | `"ongoing"` | `"daily"` |
| `"ตอนใหม่ทุกอังคาร"` | `"ongoing"` | `"tue"` |
| `"ตอนใหม่ทุกศุกร์"` | `"ongoing"` | `"fri"` |
| `"ตอนใหม่ทุกเสาร์"` | `"ongoing"` | `"sat"` |
| `"จบแล้ว"` | `"ended"` | `null` |

หมายเหตุให้หน้าบ้าน: ป้าย "ใหม่" วันนี้ขึ้นเมื่อ `status === 'ตอนใหม่ทุกวัน'` (`design/v2/lib.mjs:180`) หลังย้ายแล้วเงื่อนไขเดียวกันคือ `releaseDay === 'daily'`

**และอาการที่ย่อหน้านี้เตือนไว้ ตอนนี้มีตัวจริงอยู่ในรีโปแล้ว — ผมตรวจไฟล์เอง (23 ต.ค. 2026):** อะแดปเตอร์ของ generator ที่ `build/content.mjs:34` แปลง `releaseDay` ของสัญญากลับเป็น**ข้อความไทย** (`'ตอนใหม่ทุก' + DAY_TH[...]`) แล้ว `build/content.mjs:99-100` ถอดวันออกจากข้อความนั้นอีกที ด้วยตาราง `DAY` ที่มีแค่ 4 คีย์ (`ทุกวัน` `ศุกร์` `เสาร์` `อังคาร`) — ขาด `จันทร์` `พุธ` `พฤหัสบดี` `อาทิตย์` ซึ่ง `DAY_TH` สร้างได้ ⇒ เรื่องที่ `status:"ongoing"` + `releaseDay:"wed"` **ผ่าน V5 แต่ `releaseDay(s)` คืน `null` เงียบ ๆ** แล้วไปโผล่ใต้หัวข้อ `"จบแล้ว ไม่มีตอนใหม่"` ที่ `build/pages-discovery.mjs:417-418` และหลุดจาก CollectionPage ของหน้าตารางด้วย (`:401` ใช้แค่ `daily`+`weekly`)

วันนี้ยังไม่ระเบิดเพราะข้อมูลจริงมีแค่ 4 ค่าตามตารางข้างบน **มันจะระเบิดวันแรกที่มีคนในแผง admin เลือกวันพุธ** — ซึ่งคือเหตุผลที่สัญญานี้เก็บ `releaseDay` เป็น enum ตั้งแต่ต้น ทางแก้จึงไม่ใช่เติมคีย์ลงตาราง `DAY` แต่คือ **ส่ง `releaseDay` ของสัญญาผ่านอะแดปเตอร์ตรง ๆ ไม่ต้องถอดจากข้อความไทยอีก** (เป็นงานของ Dev-Claude เจ้าของ `build/` ไม่ใช่การแก้สัญญา)

#### 6.3.2 หนึ่งตอน (`episodes[]`) และธงล็อกที่ต้องหายไป

```json
{ "n": 1, "title": "คืนพายุที่สวนก้าน", "durationSec": 166 }
```

| ฟิลด์ | ชนิด | กฎ |
|---|---|---|
| `n` | integer | ✅ เริ่มที่ 1 · เรียงขึ้นต่อเนื่องไม่ข้ามเลข ไม่ซ้ำ · `n` สุดท้ายต้องเท่ากับ `eps` (กฎ V4) |
| `title` | string | ✅ 1–80 ตัวอักษร ตัดช่องว่างแล้วไม่ว่าง |
| `durationSec` | integer | ✅ **จำนวนวินาที ไม่ใช่สตริง `"m:ss"`** · ช่วงที่รับ 30–600 (ของจริงวันนี้อยู่ที่ 85–194 วินาที) · การจัดรูปเป็น "2:46" เป็นหน้าที่หน้าบ้าน |

**ธงล็อกตอนต้องหายไปจากสัญญานี้ ไม่มีฟิลด์ใดแทนมัน** ตามมติดูฟรีทุกตอน

เรื่องที่ Dev-Codex ต้องระวังตอน migrate และผมย้ำเพราะอ่านผิดได้ง่ายมาก: tuple เดิมคือ `[ชื่อ, "m:ss", ธง]` และ **ธงตัวที่สามหมายถึง "ดูได้" ไม่ใช่ "ล็อก"** — `assets/app.js:118` ใส่คลาส `lock` เมื่อ `x[2]` เป็น**เท็จ** และ `assets/app.js:123` เด้ง `'ตอนนี้สำหรับสมาชิก'` เมื่อ `!s.episodes[ep-1][2]` นับจริงคือ `true` 120 ตอน `false` **298 ตอน** แปลว่าวันนี้ล็อกอยู่ 298 ตอน

เพราะ migration ที่ถูกต้องคือ **ทิ้งช่องที่สามไปทั้งหมด** ไม่ใช่แปลงมันเป็นอะไร ทิศของธงจึงไม่ควรมีผลต่อผลลัพธ์เลย — ผมเขียนไว้เพื่อให้ถ้าใครเผลอคิดจะ "เก็บไว้ก่อน" จะได้รู้ว่าค่าที่เก็บไว้มันกลับทิศจากชื่อที่เดา และ 298 ตอนที่ยังล็อกอยู่คือเหตุผลที่ต้องทิ้ง

4. **ห้ามเอาการแมป trope ไปฝังในโค้ดแอป** แบบที่ `design/v2/lib.mjs:29-36` ทำ (ซึ่งถูกต้องสำหรับม็อกอัพ แต่ผิดสำหรับของจริง) trope ต้องมาจากข้อมูลเท่านั้น
5. ค่า 3 กลุ่มที่ Visual เดาไว้ (`revenge-karma`, `hidden-identity`, `reborn`) **ถือเป็นข้อเสนอ ไม่ใช่ของที่ยืนยันแล้ว** ให้ AIO-20 เป็นคนตัดสิน

**อัปเดต 23 ต.ค. 2026 — AIO-20 ปิดแล้ว และค่าลงข้อมูลจริงแล้ว** ผมตรวจ `assets/data.js` เอง: ทะเบียน `tropes` มี **13 slug** (`revenge-karma` `comeback` `inheritance` `fruit-drama` `hidden-identity` `ghost` `cross-class-love` `boss-secretary` `reborn-novel` `period` `forbidden-love` `bullied` `murder-mystery`) และทั้ง **12/12 เรื่องมี `tropes` ไม่ว่าง** (0 เรื่องที่ยังว่าง) ⇒ ข้อ 3 ข้างบนเกิดขึ้นแล้วตามที่วางไว้ และข้อ 5 จบ: `reborn` ที่ Visual เดา กลายเป็น `reborn-novel` ในของจริง ซึ่งเป็นเหตุผลที่สัญญาไม่ยอมให้ฝังการแมปไว้ในโค้ด (ข้อ 4)

เหลือสิ่งเดียวที่ยังต้องทำกับ trope คือ **ย้ายค่าพวกนี้เข้า `content.json` ตอน migrate** พร้อมกฎ V3 (ทุกค่าต้องมีในทะเบียน) — ไม่ใช่การรอใครอีกแล้ว

### 6.6 ของที่ "ห้าม" อยู่ใน `content.json`

ข้อนี้สำคัญเท่ากับรายการฟิลด์ที่ต้องมี

`assets/data.js` วันนี้มีคีย์บนสุด 5 ตัว: `genres`, `subs`, `series`, `following`, `cont` — **สองตัวท้ายไม่ใช่ข้อมูลของเว็บ** `following` คือรายการเรื่องที่ผู้ชมติดตาม (5 เรื่อง) และ `cont` คือตอนที่ดูค้างไว้ (4 เรื่อง) มันถูก ship มาเป็นข้อมูลตัวอย่างสำหรับม็อกอัพ ซึ่งถูกต้องสำหรับม็อกอัพ แต่ถ้ามันหลุดเข้า `content.json` จะกลายเป็น "ทุกคนที่เปิดเว็บเห็นว่าตัวเองติดตาม 5 เรื่องเดียวกัน" และแย่กว่านั้นคือเป็นก้าวแรกของการมีบัญชีผู้ชม ซึ่งมติข้อ 2 ตัดถาวร

| ห้ามมี | เพราะ | ที่ถูกต้องคือ |
|---|---|---|
| `following` · `cont` · ประวัติการดู · ความคืบหน้าในตอน | เป็นของรายคน · มติข้อ 2 | `localStorage` ของเบราว์เซอร์ผู้ชมเท่านั้น |
| อะไรที่ระบุตัวบุคคลของผู้ชมได้ (ชื่อ อีเมล id อุปกรณ์) | ไม่มีบัญชีผู้ชม จึงไม่มีเหตุให้เก็บ | ไม่เก็บเลย |
| `freeEps` · `coinPerEp` · ธงล็อก · ราคา · ชั้นสมาชิก | มติข้อ 1 · กฎ V8 | ไม่มี |
| `subs` (ซับตัวอย่าง) | ไม่มีไฟล์วิดีโอให้ซับเกาะ (`<video` = 0) ใส่ไปตอนนี้คือข้อมูลที่ไม่มีความหมาย | เก็บไว้พิจารณาใน ADR-002 ตาม §3.2 |
| ข้อความที่ประกอบขึ้นได้จากฟิลด์อื่น เช่น "24 ตอน" "ตอนใหม่ทุกศุกร์" "12.4M วิว" | ข้อมูลซ้ำสองที่ = เดี๋ยวก็ไม่ตรงกัน ซึ่งเป็นปัญหาเดิมที่เรากำลังแก้ | หน้าบ้านประกอบจาก `eps` `releaseDay` `views` |

### 6.7 ที่ว่างสำหรับวิดีโอ — เตรียมไว้แต่ยังไม่เปิด

ตาม §3.2 ถ้าคำตอบลูกค้าออกมาว่ามีคลิปจริง `content.json` จะต้องอ้างถึงไฟล์วิดีโอได้ ผมจึงล็อกไว้ล่วงหน้าว่าตอนนั้นให้เพิ่มเป็น **ฟิลด์ไม่บังคับใน `episodes[]`** (ไม่ใช่โครงใหม่ ไม่ใช่ขยับ `version`) เพื่อให้ของที่ Dev เขียนวันนี้ไม่ต้องรื้อ

เงื่อนไขของการเติม: **ต้องมี ADR-002 อนุมัติก่อน** เพราะมันมีค่าแบนด์วิดท์ต่อเดือนที่ขึ้นกับจำนวนคนดู และเรื่องเงินเป็นของลูกค้า — ห้ามเติมฟิลด์วิดีโอเข้ามาโดยถือ ADR-001 เป็นฐาน

### 6.8 เส้นแบ่งหน้าที่ระหว่าง Dev-Codex กับ Dev-Claude

| | Dev-Codex (หลังบ้าน) | Dev-Claude (หน้าบ้าน) |
|---|---|---|
| `content.json` | **ผลิต** | **อ่าน ห้ามเขียน** |
| ตัวตรวจ V1–V11 | เจ้าของ | รันได้ แต่ไม่ใช่เจ้าของ |
| migrate จาก `assets/data.js` | เจ้าของ (รวมการทิ้งธงล็อก 298/418 ตาม §6.3.2) | — |
| เขียน `synopsis` ใหม่ 12 เรื่อง | เจ้าของเครื่องมือที่ให้พิมพ์ | — |
| จัดรูป `durationSec` → "2:46" | — | เจ้าของ |
| ย่อ `views` → "12.4M" | — | เจ้าของ |
| ประกอบข้อความ `status`+`releaseDay` → "ตอนใหม่ทุกศุกร์" | — | เจ้าของ |

**หมายเหตุบังคับสำหรับ Dev-Claude** — มติข้อ 3 เกิดจากของจริงที่ยังอยู่ในรีโป: `watch/*.html` ทั้ง 12/12 ไฟล์มี `<h1 id="epTitle"></h1>` ว่างใน HTML (`watch/ceo-cold.html:36`) แล้วให้ JS เติมตอนรัน (`assets/app.js:111`) ห้ามทำซ้ำรูปแบบนี้ เกณฑ์ตรวจง่าย ๆ ที่ใช้ได้เลย: **ปิด JavaScript แล้วเปิดไฟล์ HTML ที่ build ออกมา ต้องอ่านชื่อเรื่อง ชื่อตอน และเรื่องย่อได้ครบ**

สังเกตว่าวันนี้ยังไม่มี JSON-LD ในรีโปเลย (0 ไฟล์) — structured data ทั้งหมดเป็นของใหม่ที่ Dev-Claude จะเขียน ไม่มีของเก่าให้แก้ ดังนั้น §7 เป็นกฎที่บังคับได้ตั้งแต่บรรทัดแรก ไม่ใช่การตามเก็บ

## 7. `views` กับ structured data — ห้ามเมื่อไร ปลดเมื่อไร

### 7.1 สภาพวันนี้: ห้าม

`views` ไม่มีอยู่ใน `assets/data.js` เลย (0/12 เรื่อง) ตัวเลขที่เห็นในม็อกอัพที่อนุมัติมาจากสตริง 12 ค่าที่ฝังไว้ที่ `design/v2/lib.mjs:22-27` และคอมเมนต์ที่ `design/v2/lib.mjs:18-21` ก็เขียนตรง ๆ ว่าเป็นตัวเลขตัวอย่าง ไม่มีระบบวัดอยู่จริงแม้แต่ชิ้นเดียว

ดังนั้นตามมติข้อ 5:

- **โชว์ในหน้าได้** ตามแบบที่อนุมัติ และหน้าที่โชว์ต้องมีหมายเหตุกำกับว่าเป็นตัวเลขตัวอย่าง ตามที่ `design/v2/lib.mjs:20-21` กำหนดไว้แล้ว
- **ห้ามเข้า structured data ที่ส่งให้ Google** เด็ดขาด — ห้ามใส่ `interactionStatistic` / `InteractionCounter` / `aggregateRating` / `ratingValue` / `reviewCount` หรือฟิลด์ทำนองเดียวกันใน JSON-LD
- ค่าในไฟล์ต้องเป็น `null` ไม่ใช่ตัวเลขเดา และ `meta.viewsSource` ต้องเป็น `"none"` (กฎ V10 บังคับให้สองอย่างนี้ตรงกันเสมอ)

เหตุผลที่เข้มข้อนี้: ตัวเลขที่ส่งให้ Google คือการยืนยันข้อเท็จจริงต่อบุคคลที่สาม ส่งตัวเลขที่ไม่มีระบบวัดรองรับคือการให้ข้อมูลเท็จ และโทษของมันตกที่เว็บของลูกค้า ไม่ใช่ตกที่เรา

### 7.2 เงื่อนไขปลดล็อก — ต้องครบทุกข้อ ขาดข้อเดียวคือยังห้าม

ข้อห้ามนี้ปลดเฉพาะฟิลด์ที่วัดจริง ไม่ได้ปลดทั้งหมวด เงื่อนไขเขียนให้เครื่องตรวจได้:

1. มีตัวนับที่ทำงานอยู่จริงบนระบบที่ให้บริการจริง ไม่ใช่ตัวเลขที่คนพิมพ์
2. มีเอกสารกำกับว่า "หนึ่งวิว" นับอย่างไร (นับเมื่อไหร่ · กัน bot อย่างไร · คนเดิมดูซ้ำนับไหม · นับรวมช่วงเวลาไหน) — ถ้าตอบไม่ได้ว่านับอย่างไร ก็ยังไม่เรียกว่าวัดจริง
3. ค่าใน `content.json` ไหลมาจากตัวนับนั้นโดยอัตโนมัติ ไม่มีมือคนแตะกลางทาง
4. `meta.viewsSource` เปลี่ยนเป็น `"analytics"` และ **ตัวตรวจ V10 ต้องผ่าน** คือไม่มี `views` ที่เป็น `null` ค้างอยู่
5. มีเวลาที่วัดกำกับอยู่ด้วย เพื่อให้รู้ว่าตัวเลขเก่าแค่ไหน
6. CTO บันทึกการปลดใน ADR นี้เป็นการแก้ไขที่มีวันที่ **การปลดไม่เกิดเองจากการที่โค้ดพร้อม**

ครบหกข้อแล้ว **`views` เข้า JSON-LD ได้เฉพาะฟิลด์ `views` ตัวเดียว** — `aggregateRating` และคะแนนรีวิวทุกชนิด **ยังห้ามอยู่** เพราะเว็บนี้ไม่มีระบบรับคะแนนจากผู้ชมเลย และจะไม่มี เพราะไม่มีบัญชีผู้ชม (มติข้อ 2) การปลดข้อหนึ่งไม่ลากข้ออื่นตามไปด้วย

### 7.3 สิ่งที่ยังใส่ structured data ได้วันนี้

ข้อห้ามจำกัดอยู่ที่ตัวเลขที่ไม่มีระบบวัด ไม่ได้ห้าม structured data ทั้งหมด ข้อมูลที่เป็นข้อเท็จจริงจากข้อมูลจริงใส่ได้: ชื่อเรื่อง · เรื่องย่อ · จำนวนตอน · แนว · ตอนและชื่อตอน · ความยาวตอนจาก `durationSec` · ภาพปก ทั้งหมดนี้ตรวจย้อนได้จาก `content.json` จึงไม่ใช่การกล่าวอ้างลอย ๆ

## 8. ขอบเขตปฏิบัติการ: เอกสารนี้ไม่ deploy ไม่ตั้งโดเมน ไม่ซื้ออะไร

ตามมติข้อ 4 เอกสารนี้**ไม่มีคำสั่งปฏิบัติการใด ๆ** ไม่มีคำสั่ง deploy ไม่มีการตั้งโดเมน ไม่มีการจัดซื้อ ตัวเลขใน §4.4 เป็นราคาตั้งสาธารณะเพื่อให้ลูกค้าเปรียบเทียบทางเลือกได้ ไม่ใช่การเลือกผู้ให้บริการและไม่ใช่การขออนุมัติงบ เรื่องเงินเป็นของลูกค้า

เส้นที่เอกสารนี้หยุด: **ADR-001 จบลงที่ "มีไฟล์ HTML ที่ build ออกมาถูกต้องและผ่านตัวตรวจ V1–V11"** การเอาไฟล์นั้นขึ้นที่ไหนเป็นงานของ DevOps และอยู่นอกเอกสารนี้

และเพื่อให้คนอ่านไม่เข้าใจผิดว่า §9 คือใบเบิกทางขึ้นของจริง ขอบันทึกสภาพจริงไว้:

- การที่ผมอนุมัติให้ merge **ไม่ใช่การอนุมัติให้ deploy** เป็นสองประตูแยกกัน
- DevOps ขึ้น **staging** ได้เองไม่ต้องขอ · ขึ้น **production** ต้องได้อนุมัติจาก CEO หรือบอร์ดก่อน ทุกครั้งต่อหนึ่งการขึ้น
- **บันทึกมติบอร์ด 22 ต.ค. 2026:** บอร์ดให้ EX-001 และ EX-002 **หมดอายุ** วันที่ 5 พ.ย. 2026 โดยไม่ทำการย้ายไปบัญชีแยกให้จบ และยืนยันว่าการปลดการระงับเป็นการกระทำของบอร์ดเอง ผลคือ **ตั้งแต่ 6 พ.ย. 2026 บริษัทไม่มีเส้นทางเข้าสู่ production ที่ถูกระเบียบ** และการระงับ production session ยังมีผลอยู่ ข้อนี้บันทึกไว้ในฐานะมติของบอร์ดที่มีวันที่ ไม่ใช่การร่างกฎของผมเอง และเอกสารนี้ไม่ได้ขอต่ออายุหรือขอข้อยกเว้นสืบทอดใด ๆ
- ผลต่องานนี้ตรงไปตรงมา: **การวางแผนและทำงานตาม ADR นี้เดินได้ปกติ** เพราะงานทั้งหมดจบที่ build artifact การขึ้น production เป็นเรื่องที่บอร์ดถือไว้ และไม่ใช่สิ่งที่ ADR นี้ต้องหาทางออกให้

## 9. เส้นทางเผยแพร่ — ใครรัน rebuild และเมื่อไร

### 9.1 เส้นทาง

```
ทีมงานแก้ข้อมูลในแผง admin   (คนกด · §5 ยืนยันตัวตนแล้ว)
        │
        ▼
แผงตรวจ V1–V11 ในเบราว์เซอร์ก่อนให้กดบันทึก   (เจอผิดตรงนั้น ไม่ปล่อยให้ CI เจอ)
        │
        ▼
เขียน content.json เป็น commit หนึ่งก้อน   (ผู้แก้ = commit author ได้ร่องรอยฟรี)
        │
        ▼
CI ตื่นเพราะ commit นั้น  →  รัน V1–V11 อีกรอบเป็นตัวตัดสิน   (ผิด = ล้ม ไม่ build ต่อ)
        │
        ▼
build HTML static ใหม่ทุกหน้าที่เกี่ยวข้อง  →  ตรวจ V11 (ปิด JS แล้วต้องอ่านเนื้อหาได้)
        │
        ▼
เป็น build artifact ที่พร้อม  ←── ADR-001 จบที่บรรทัดนี้
        ┆
        ┆   (นอกขอบเขตเอกสารนี้ · §8)
        ▼
DevOps เอาขึ้น staging ได้เอง · ขึ้น production ต้องให้ CEO/บอร์ดอนุมัติต่อครั้ง
```

### 9.2 ใครรัน และเมื่อไร

| คำถาม | คำตอบ |
|---|---|
| ใครกดให้เริ่ม | ทีมงานที่แก้ข้อมูล โดยการบันทึกในแผง admin ไม่มีใครต้องรันคำสั่งด้วยมือ |
| ใครรัน rebuild จริง | **CI** ไม่ใช่คน · DevOps เป็นเจ้าของ CI |
| เมื่อไร | **อัตโนมัติเมื่อมี commit ที่แตะ `content.json`** ไม่มีตารางเวลา ไม่ต้องรอใครสั่ง |
| ตรวจ V1–V11 กี่รอบ | สองรอบ — ในแผงเพื่อให้คนแก้รู้ทันที และใน CI เป็นตัวตัดสิน · **รอบใน CI ข้ามไม่ได้** เพราะรอบในเบราว์เซอร์เชื่อถือไม่ได้โดยธรรมชาติ |
| ตรวจไม่ผ่านแล้วอย่างไร | build ล้ม ไม่มี artifact ออกมา ของเดิมที่ให้บริการอยู่ไม่ถูกแตะ |
| ข้อมูลผิดหลุดไปแล้วแก้อย่างไร | `git revert` commit นั้น แล้ว CI build ของเดิมกลับมาเอง — นี่คือข้อได้เปรียบของทางเลือก A ที่ทาง B/C ต้องสร้างเอง |
| ใครอนุมัติให้โค้ด (ไม่ใช่ข้อมูล) เข้า main | CTO · ต้องผ่านรีวิวสองฝั่งครบ และผ่าน Security sign-off สำหรับส่วน §5 ตาม §5.3 |
| การแก้ข้อมูลต้องรีวิวสองฝั่งไหม | **ไม่ต้อง** — รีวิวสองฝั่งคือเกณฑ์สำหรับการเปลี่ยนโค้ด การแก้ชื่อตอนคือการแก้เนื้อหา ตัวตรวจ V1–V11 เป็นประตูของมัน · ถ้าการแก้ข้อมูลครั้งนั้นต้องเปลี่ยน schema ด้วย นั่นคือการเปลี่ยนโค้ด ต้องรีวิวสองฝั่งและต้องแก้ ADR นี้ก่อน |

### 9.3 ลำดับงานที่ปลดล็อกแล้ว ทำขนานกันได้

เมื่อ §6 เป็นสัญญาที่ตกลงแล้ว สองฝั่งเริ่มพร้อมกันได้ทันทีโดยไม่ต้องรอกัน:

- **Dev-Codex เริ่มได้เลย** — ตัวตรวจ V1–V11 · migration จาก `assets/data.js` (ทิ้งธงล็อก · แปลง `"m:ss"` → `durationSec` · แยก `status`/`releaseDay` ตามตารางใน §6.3.1) · แผง admin + auth §5
- **Dev-Claude เริ่มได้เลย** — อ่าน `content.json` ตาม §6 แล้วประกอบ HTML ให้มีเนื้อหาจริงตอนส่ง · เขียน JSON-LD ตาม §7.3 (ไม่มี `views`) · ใช้ไฟล์ `content.json` ตัวอย่างที่ Dev-Codex ส่งให้ก่อนของจริงเสร็จได้
- **งานที่รอของจากคนอื่นจริง ๆ เหลือชิ้นเดียว** — `synopsis` 12 เรื่องที่ต้องมีคนเขียนเนื้อหาใหม่ เพราะวันนี้ไม่มีอยู่เลย (0/12) และ `hook` ใช้แทนไม่ได้ตามกฎ V7 · ค่า `tropes[]` ไม่รออีกแล้ว AIO-20 ปิดและลงข้อมูลครบ 12/12 (§6.5)
- **คำถาม §3.2 ได้คำตอบแล้ว** — "ยังไม่มีคลิป ขอจัดระเบียบข้อมูลก่อน" (§3.3) จึงไม่มีงานวิดีโอเข้าคิว และไม่มีอะไรรออยู่หน้างานทั้งสองฝั่งอีก

## 10. ผลที่ตามมา

**ได้อะไร**

- แหล่งความจริงแหล่งเดียว แก้ชื่อเรื่องที่เดียวแล้วทุกหน้าตรงกัน ปัญหาข้อมูลซ้ำสองที่หมดไป
- ค่าใช้จ่ายคงที่ 0 THB/เดือนในชั้นฟรี เพดานหลักร้อยตอนโต เหมาะกับเว็บที่ไม่มีรายได้จากผู้ชม
- สองฝั่ง Dev เดินขนานกันได้จริงเพราะมีสัญญาเดียวกั้นกลาง
- มติดูฟรีและมติไม่มีบัญชีผู้ชมถูกบังคับด้วยเครื่อง (V8/V9) ไม่ใช่ด้วยความจำของคน
- ธงล็อก 298 ตอนที่ยังขัดมติอยู่ในโค้ด จะหายไปพร้อม migration ไม่ใช่ค้างอยู่เงียบ ๆ

**เสียอะไร / รับอะไร**

- แก้ข้อมูลแล้วเห็นผลช้าเท่าเวลา build ไม่ทันที — รับได้ เพราะเนื้อหาละครไม่ใช่ข้อมูลที่ต้องสด
- คนแก้ข้อมูลพร้อมกันหลายคนจะชน — รับได้ตอนนี้ ถ้าวันหนึ่งมีฝ่ายคอนเทนต์หลายคน ย้ายไปทางเลือก B โดยหน้าบ้านไม่ต้องแก้ (§4.6)
- ต้องมีคนเขียน `synopsis` 12 เรื่องใหม่ เป็นงานเขียนจริง ไม่ใช่งานโค้ด และบริษัทไม่มีฝ่ายคอนเทนต์ — เป็นต้นทุนที่ต้องยอมรับ เพราะถ้าไม่เขียน หน้ารายละเอียดก็ยังซ้ำประโยคโปรยอยู่เหมือนเดิม
- `design/v2/` จะต่างจากของจริงเรื่องรูปข้อมูล (tuple กับ object) โดยตั้งใจ — ม็อกอัพเป็นของที่อนุมัติแล้วและ Visual เป็นเจ้าของ ห้ามแก้ ให้ถือเป็นภาพอ้างอิง ไม่ใช่โค้ดที่ต้องตามสัญญานี้
